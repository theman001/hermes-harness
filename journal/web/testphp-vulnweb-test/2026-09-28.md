**1. 추론 근거**

phase 2 첫 라운드. phase 1의 "다음 수정 방향" 목록(stored XSS 재승인 · traversal 잔여 ·
Register 검증 · second-order)을 그대로 반복하기 전에, 먼저 **phase 1 결론 자체를 재검증**
하는 쪽이 ROI가 높다고 판단했다. 이유는 두 가지다.

(a) phase 1의 "UNION-based 는 컬럼수 1~15 전부 500 → 사용 불가" 결론은 **근거가 약하다**.
소스를 보면 `Search.asp` 의 주입 지점은 `AND (CHARINDEX(a.title, '<st>')>0 OR
CHARINDEX(a.message,'<st>')>0)` 처럼 **괄호 안 문자열 리터럴**이고, 같은 값이 두 번 들어간다.
`0 UNION SELECT ...--` 를 그냥 넣으면 앞부분 따옴표·괄호가 닫히지 않아 500이 나는 게 당연하다
— 즉 "UNION 이 막혔다"가 아니라 "페이로드가 틀렸다"였을 가능성이 크다. `Search.asp` 는
파라미터가 **쿼리 1개에만** 쓰이므로(showforum/showthread 는 컬럼 수가 다른 3~4개 쿼리에
같은 id 재사용 → UNION 컬럼수 정합 불가) UNION이 성립하면 **블라인드 없이 페이지에 데이터가
렌더되는** 최상급 PoC가 된다.

(b) phase 1은 SQLi를 "boolean-blind 읽기"로 규정했지만, `;` 로 문장을 이어붙이는
**stacked query** 여부는 제대로 확인되지 않았다(기록에는 "세미콜론 변형 500"만 있음).
stacked가 되면 심각도가 '데이터 읽기'에서 '임의 T-SQL 실행(+앱 테이블 쓰기)'으로 올라간다.

부수적으로 **쓰기 없는** 신규 표면도 확인했다: `Login.asp:37` 이 `Session.Contents("uname")
= Request.Form("tfUName")` 로 입력값을 검증 없이 세션에 넣고 모든 페이지 메뉴가 그 값을
HTML 인코딩 없이 출력한다 → 로그인 1회로 성립하는 XSS(쓰기 불요). phase 1은 세션에 값이
그대로 들어간다는 것(`logout admin'--`)만 관찰하고 XSS 페이로드는 시도하지 않았다.

RAG 검색(`mcp__rag__search`)은 이번 라운드 3회 시도했으나 **전부 0건**(rag_entries가 아직

**3. 결과**

**(①) `/Register.asp` SQLi — 확정 (주입 + stacked + 데이터 조작 3중 증명)**

| 단계 | 결과 |
|---|---|
| 사전 | 기존 정상등록 계정의 `avatar` = `''` (정상 경로는 항상 빈 값) |
| 주입 | POST `/Register.asp` → **302 `Location: Login.asp?RetURL=`** 이며 **4.35초**(= 뒤에 붙인 `IF 1=1 WAITFOR DELAY '0:0:04'` 가 실행됨 → Register 에서도 **stacked query 성립**) |
| 검증 A | UNION 추출: `SELECT avatar FROM users WHERE uname='acu-r9-reg'` = **`INJECTED`** ← 정상 경로로는 절대 불가능한 값. 행 수 1 |
| 검증 B | 정상 로그인 폼으로 `acu-r9-reg` / `RegR9!` → **302 `Location: Default.asp`**, `/Default.asp` 메뉴에 `logout acu-r9-reg` |

→ INSERT 문을 재구성해 **서버가 원래 넣으려던 값이 아닌 값을 넣게 만들었다**. 계정 생성
엔드포인트 하나로 임의 값의 계정을 만들 수 있고(예: `alevel`/`avatar` 조작), 로그인까지 된다.

**(②) second-order — 확정(단, 임팩트는 "게시 기능 파괴"로 한정)**

| 세션 사용자명 | 로그인 | 답글 POST |
|---|---|---|
| `acu-r7 proof`(정상 계정, Round 8) | 302 | **200, 게시글 생성됨** (대조군: 게시 경로 정상) |
| `x' OR 1=1--` (SQLi 우회) | 302 + 인증됨 | **500** (게시글 미생성) |
| `x' OR '1'='1'--` (SQLi 우회) | 302 + 인증됨 | **500** (게시글 미생성) |
| `x'; WAITFOR DELAY '0:0:04'--` | 200(로그인 실패) + **4.37초 지연** | — |

- 500 이 나온 이유는 소스 그대로다: 게시 INSERT 는 `poster = '" & Session.Contents("uname") & "'`
  로 **사용자명을 이스케이프 없이** 넣는다(`Replace(...,"'","''")` 는 tfSubject/tfText 에만 적용).
  따옴표가 포함된 사용자명(=로그인 우회로 세션에 들어간 문자열)이 INSERT 문을 깨뜨린다 →
  **second-order 주입 확정**(같은 값이 다른 문장에서 SQL 로 해석됨).
- 다만 **데이터 주입(공격자가 고른 값 삽입)까지는 불가**로 확인됐다: 로그인이 성립하려면
  사용자명이 `WHERE uname='...'` 형태를 만족해야 하고, 그런 문자열은 `VALUES (...)` 목록에서는
  반드시 구문 오류가 된다(두 제약이 상호 배타적). 즉 실질 임팩트는 **인증된 세션의 게시 기능
  영구 파괴(500)** 수준이다 — 과대주장하지 않는다.
- 부수 발견: **`Login.asp` 의 `tfUName` 에서도 stacked query 가 성립**한다(`x'; WAITFOR DELAY
  '0:0:04'--` → 200 응답이 **4.37초**). 즉 인증 전 단계에서도 임의 T-SQL 문장 실행 경로가 하나 더 있다
  (로그인은 실패했지만 서버측 문장은 실행됨).

**(③) PUT 업로드 — 불가(음성 확정)**

`PUT /r10probe.txt` → **404**. `Allow` 헤더(PUT/DELETE 없음)와 일치 — IIS 가 이 메서드를
