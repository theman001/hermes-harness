**1. 추론 근거**

정찰 초반이라 가정을 세우기보다 자산 표면을 빠짐없이 훑는 것이 목적이었다. `targets/
testasp-vulnweb-full.json` 상 `testasp.vulnweb.com` 단일 도메인, `own_system` 모드,
`prohibits_automation: false`("공개적으로 보안 도구 테스트 용도로 운영되는 의도적 취약
사이트 — 스캐닝/자동화 명시적으로 허용")이므로 워드리스트 기반 대량 스캔이 정책상 허용된다.

스캔 설계 근거: (a) 디렉터리만 훑는 1차 스캔은 `.asp` 파일을 놓치므로 동일 워드리스트에
`-e` 확장자 세트를 붙인 2차 스캔을 반드시 병행(gobuster 로 교차검증까지), (b) 서버가
IIS 8.5 라서 `_vti_*`/`Trace.axd`/`web.config`/`global.asa` 같은 IIS 특정 경로를 별도
점검, (c) `-mc 200,204,301,302,307,401,403` 로 404 만 배제 — 사전 확인에서 미존재 경로가
전부 404/1245B 로 균일해서 와일드카드 오탐 위험이 없음을 확인한 뒤 진행.

프록시: 지시대로 `-x http://127.0.0.1:8080` (Burp) 을 우선 사용. 1차 벤치마크에서 프록시
경유 ~40 req/s vs 직접 ~360 req/s 로 9배 차이가 나서 스레드를 올려 추가 측정한 결과
프록시는 30→60→120 스레드에서도 ~50 req/s 로 포화됨을 확인(프록시가 병목). 47만 요청짜리
`-e` 스캔은 프록시로 약 2.5시간이 걸려 비현실적이라 **프록시 없이 직접 수행**하고 그 사실을
보고에 명시하기로 판단. 프록시 경유로 실행한 것은 ffuf 1차 스캔과 gobuster 스캔.

**1. 추론 근거**

nikto 알림 본문에 Round 1 결과에 없던 두 가지가 보였다: (a) `/index.aspx` + `x-aspnet-version: 2.0.50727`, (b) `Allow: OPTIONS, TRACE, GET, HEAD, POST`. (a)는 내 스캔의 확장자 세트가 `.asp` 계열만이고 **`.aspx` 가 빠져 있었다**는 뜻일 수 있어 — 그렇다면 커버리지 공백(false negative)이므로 즉시 확인해야 한다. (b)는 TRACE 활성 시 XST 라는 실제 취약점이므로 실제 동작을 확인해야 한다. 도구 출력은 자기보고이므로 재현으로만 채택한다는 원칙에 따라 6개 명제를 각각 독립 검증했다.

**4. 피드백**

- 교차검증 방식이 유효했다: nikto 13항목 중 **1건 오탐(`/index.aspx`)**, **1건 과대평가(TRACE)**, **1건 재현 성공(10.0.0.14)**, 5건은 기존 확인과 일치, 1건 미확인. 도구 출력을 그대로 보고서에 넣었다면 존재하지 않는 ASP.NET 엔드포인트와 실행 불가능한 XST 를 보고할 뻔했다.
- 커버리지 공백은 **실재했지만 결과는 부정적**이었다 — `.aspx` 세트가 빠진 것은 사실이나 그 축에 파일이 없어서 최종 발견 집합은 변하지 않았다. 즉 Round 1 결과의 타당성은 유지되지만, "확장자 세트를 잘못 골랐을 수 있다"는 위험은 실제로 존재했음이 드러났다.
- 부수적으로 이전 관찰이 정정됐다: "404 가 전 확장자 균일 1245B" 는 테스트한 12종에 한정된 사실이고 `.aspx/.axd` 는 다른 크기(1505/1510B)를 반환한다. 다만 `-mc` 로 404 를 배제했기 때문에 오탐에는 영향이 없었다.

**5. 다음 수정 방향**

1. IIS/ASP.NET 타겟 스캔 시 확장자 세트를 **`.asp` + `.aspx, .ashx, .asmx, .ascx, .axd, .svc, .aspx`** 로 확장하는 것을 기본값으로 한다(이번엔 결과가 0이었지만 누락이 false negative 를 만드는 구조적 위험이 확인됨).

3. `X-AspNet-Version: 2.0.50727` → ASP.NET 2.0 알려진 취약점(ViewState MAC, Padding Oracle 등) 목록을 tech-docs 로 조회해 다음 라운드 우선순위 결정.

## Round 3 — 2026-09-23T06:10:00Z

**라운드 성격**: 도구 환경 버그 근본원인 규명 라운드 (재현 실험). exploit 시도 없음 → `attempted_exploits.json` 갱신 없음.

**1. 추론 근거**

Round 1 의 하위 디렉터리 루프가 9개 결과를 `subdirs/.json` 한 파일에 덮어쓴 사건을 "변수가 소실됐다"고만 적어두었는데, background 프로세스 완료 알림이
`Referenced but unset environment variable evaluates to an empty string: d` 를 함께 보여줬다. 즉 원인이 *실행 경로 특이적*일 수 있어, 같은 명령을 foreground/background 두 경로에서 돌려 대조 실험했다. 이 함정은 이 환경의 모든 루프 스캔에 재발하므로 정확한 조건을 알아야 했다.

**2. 사용 코드**

```bash
# background 경로 (background=true 로 실행)
mkdir -p /tmp/full/sub5/vartest
for d in aa bb cc; do echo "bg url=http://x/$d/FUZZ out=/tmp/full/sub5/vartest/bg-${d}.txt" > /tmp/full/sub5/vartest/bg-${d}.txt; done

# foreground 대조군 (같은 구조, 변수명만 다르게)
mkdir -p /tmp/full/sub5/vartest2
for d in aa bb cc; do echo "fg url=http://x/$d/FUZZ out=/tmp/full/sub5/vartest2/fg-${d}.txt" > /tmp/full/sub5/vartest2/fg-${d}.txt; done
ls -la /tmp/full/sub5/vartest/ /tmp/full/sub5/vartest2/
```

**3. 결과**

| 실행 경로 | 결과 |
|---|---|
| background=true | **`bg-.txt` 1개만 생성**, 내용 `bg url=http://x/cc/FUZZ out=/tmp/full/sub5/vartest/bg-.txt` (마지막 반복만 남음) |
| foreground | `fg-aa.txt`, `fg-bb.txt`, `fg-cc.txt` **3개 정상 생성** |

→ background 경로에서 출력 경로의 **braced `${d}` 가 스냅샷 시점에 빈 문자열로 치환**되고,
런타임 unbraced `$d`(URL 부분)는 정상 동작한다. Round 1 에서 `subdirs/.json` 안에 마지막
반복인 cgi-bin 결과만 남아 있었던 것과 서명이 정확히 일치한다.

**4. 피드백**

- 성공. 환경 특이 버그를 재현 조건까지 확정했다. 최초 서술("셸 루프 변수가 소실")은 부정확했다 — unbraced 변수는 background 에서도 정상이므로, 원인은 **braced 보간 + background 경로 조합**이다.
- 영향 범위: 이 함정은 도구(ffuf/gobuster) 문제가 아니라 Hermes terminal 도구의 background 실행 경로 문제이므로, 모든 루프·다중 대상 스캔에 재발한다. 결과 파일이 1개만 생기는데 스캔 자체는 성공(exit 0)하므로 **조용히 데이터를 잃는다** — 가장 위험한 유형.
- 부수적으로 foreground 420초 상한 문제(nohup & 의 거짓 완료 알림)와 함께, 이번 프로젝트에서 스캔 실행 방식을 두 번 고쳐야 했다.

**5. 다음 수정 방향**

1. **규칙화**: background 작업은 `for` 루프를 명령 문자열에 넣지 않고 **스크립트 파일 + `bash script.sh`** 로만 실행한다(경로 보간이 스크립트 내부에서 bash 런타임에 일어나므로 문제가 사라짐 — `scratch/subscan.sh` 가 9개 JSON 정상 생성으로 검증됨).
