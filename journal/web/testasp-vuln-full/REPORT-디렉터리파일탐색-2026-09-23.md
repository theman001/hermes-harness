### `/_vti_cnf/` 상세 (가장 가치 있는 발견)
FrontPage 확장 메타데이터가 **403 이 아니라 200** 으로 서빙된다. 응답 본문 예:
```
vti_filesize:IR|3663
vti_timelastmodified:TR|05 Oct 2007 10:01:19 -0000
vti_cachedsvcrellinks:VX|FQUS|acuforum/styles.css ... FHUS|acuforum/Templatize.asp ...
vti_backlinkinfo:VX|acuforum/login.asp acuforum/register.asp acuforum/search.asp
                      acuforum/default.asp acuforum/showthread.asp acuforum/showforum.asp
```
- **파일 존재 오라클**: `/ _vti_cnf/<파일명>` 이 200 이면 그 파일이 실제 존재(404 와 명확히
  구분) → 워드리스트 없이도 사이트 내부 파일 목록을 확정할 수 있는 보조 오라클.
- **내부 정보 유출**: 원본 파일 크기, 최종 수정 시각(2007-10-05), 배포 경로 `acuforum/`,
  백링크로 연결된 다른 페이지 이름 목록(공개되지 않은 페이지까지 나열 가능).
- 같은 메커니즘으로 `/ _vti_cnf/<파일명>` 을 훑으면 **링크가 끊긴/삭제된 페이지의 흔적**
  도 드러날 수 있음 → 다음 라운드 확장 대상.

**기타 제약 관찰**
- ffuf#1 은 실행 셸이 도구의 420초 상한에 걸려 종료됐으나 출력 JSON 은 정상 기록됨
  (23건). ffuf#2 가 #1 을 완전 포함하므로 #1 결과 유실은 없음.
- 백그라운드 실행 시 `nohup ... &` 형태는 셸이 즉시 반환해 "완료"로 오인될 수 있음 →
  이후로는 스크립트 파일 + 프로세스 생존 확인으로 폴링.
- **백그라운드 명령에서 braced 변수(`${VAR}`)가 빈 값으로 치환됨(재현 완료)**: 하위 디렉터리
  루프를 `background=true` 로 실행했을 때 출력 경로의 `${d}` 가 스냅샷 시점에 빈 문자열로
  치환되어 9개 결과가 전부 `subdirs/.json` 한 파일에 덮어써졌다(런타임 unbraced `$d` 는 정상
  → 남은 파일이 마지막 반복인 cgi-bin 결과였음). 재현:
  `for d in aa bb cc; do echo "url=http://x/$d/FUZZ" > /tmp/vt/bg-${d}.txt; done` 를
  background 로 실행 → `bg-.txt` 1개, 내용 `url=http://x/cc/FUZZ`. **동일 명령을 foreground

  → 수정: background 작업의 루프는 `${VAR}` 경로 보간을 피하고 **스크립트 파일로 분리해
  `bash script.sh`** 로 실행(`scratch/subscan.sh` 가 그 수정판, 9개 JSON 정상 생성).

# 부록 A — 제3 도구(nikto) 교차검증 + 확장자 커버리지 보강 (2026-09-23 06:07Z)

중단) 결과가 도착해, **도구 자기보고를 그대로 채택하지 않고 항목별로 재현 검증**했다.

## A-1. nikto 주장별 검증 결과

| nikto 주장 | 재현 결과 | 판정 |
|---|---|---|
| `GET /index.aspx: x-aspnet-version: 2.0.50727` | `/index.aspx` = **404** (1505B). 헤더 `X-AspNet-Version: 2.0.50727` 자체는 404 응답에도 실제로 실림 | **오탐** (파일 없음) — 헤더 노출은 사실 |
| `OPTIONS: Allowed HTTP Methods: OPTIONS, TRACE, GET, HEAD, POST` | `OPTIONS /` 가 TRACE 를 광고하나 `TRACE /` = **501 Not Implemented** | **과대평가** (XST 불가) |
| `Location` 헤더에 RFC-1918 IP `10.0.0.14` (CVE-2000-0649) | Host 헤더 없이 HTTP/1.0 으로 요청 시 `Location: http://10.0.0.14/aspnet_client/` **재현 성공** | **사실** |
| 보안 헤더 5종 누락 (CSP/Permissions-Policy/X-Content-Type-Options/Referrer-Policy/HSTS) | 전부 부재 확인 | 일치 |
| `Default IIS server content` | `/` 는 acuforum 앱 페이지(200/3540B), `/iisstart.htm` 404 | **미확인** |
| `Microsoft-IIS/8.5 may be outdated` | 버전 확인 | 일치(정보성) |

→ 13항목 중 **1건 오탐, 1건 과대평가, 1건 재현 성공, 5건 기존 확인과 일치, 1건 미확인**.
nikto 출력을 그대로 보고서에 옮겼다면 존재하지 않는 ASP.NET 엔드포인트와 실행 불가능한
XST 를 보고할 뻔했다.

## A-2. 재현 명령 (내부 IP 노출 / Host 헤더 반사)

```bash
IP=$(getent hosts testasp.vulnweb.com | head -1 | cut -d' ' -f1)   # 44.238.29.244

# (1) Host 헤더 없이 HTTP/1.0 → 내부 사설 IP 노출
printf 'GET /aspnet_client HTTP/1.0\r\n\r\n' | nc $IP 80
#   → HTTP/1.1 301, Location: http://10.0.0.14/aspnet_client/   ← 내부 IP 10.0.0.14

# (2) Host 헤더를 주면 그 값이 Location 에 그대로 반사됨
curl -s -i --noproxy '*' -H "Host: 127.0.0.1" "http://$IP/aspnet_client"
#   → Location: http://127.0.0.1/aspnet_client/
curl -s -i --noproxy '*' -H "Host: localhost"  "http://$IP/aspnet_client"
#   → Location: http://localhost/aspnet_client/

# (3) HTTP/1.1 로 Host 없이 보내면 HTTP.sys 계층이 400 반환
printf 'GET /aspnet_client HTTP/1.1\r\n\r\n' | nc $IP 80
#   → HTTP/1.1 400 Bad Request, Server: Microsoft-HTTPAPI/2.0
```
경로가 고정 append(`/aspnet_client/`)라 즉시 오픈 리다이렉트로 악용되진 않으나, **내부 IP
노출 + Host 값 반사** 자체가 캐시 포이즈닝/호스트 헤더 인젝션 계열 검증 대상으로 등록할
가치가 있다.

## A-3. 확장자 커버리지 보강 (.aspx 계열) — 커버리지 공백 봉합

Round 1 의 확장자 세트는 `.asp` 계열만이라 **`.aspx` 가 누락**되어 있었다(nikto 의
`/index.aspx` 항목이 이 공백을 시사). 누락이 곧 false negative 이므로 즉시 보강했다.

```bash
ffuf -u http://testasp.vulnweb.com/FUZZ -w /tmp/full/wordlists/raft-small-words.txt \
  -e .aspx,.ashx,.asmx,.ascx,.axd,.svc -mc 200,204,301,302,307,401,403 -t 150 \

```

- **301,049 요청 / 결과 28행 → 루트 신규 파일 0건**

- 결론: 이 사이트에는 **ASP.NET 페이지 파일이 존재하지 않고 클래식 ASP(.asp)만 동작**한다.
  Round 1 의 파일 발견 집합은 이 축에서도 완전함이 확인됨(신규 0건 → 기존 결과 불변).

## A-4. 관찰 정정

Round 1 보고서의 **"404 가 전 경로·전 확장자에서 1245B 로 균일"** 은 실제로는 **테스트한
12종 확장자에 한정된 사실**이다. 핸들러별로 다르다:

| 확장자 | 404 크기 | 비고 |
|---|---|---|
| `.asp .txt .bak .inc .config .log .old .zip .xml .asa .htm .html` | 1245B | 클래식 ASP / 정적 핸들러 |
| `.aspx .ashx .asmx` | 1505B | ASP.NET 404 페이지 + `X-AspNet-Version` 헤더 |
| `.axd` | 1510B | ASP.NET 핸들러 |

오탐에는 영향이 없다 — 모든 스캔에서 `-mc` 로 404 를 배제했기 때문.

## A-5. 추가 사실 (검증 완료)

- **`X-AspNet-Version: 2.0.50727`** — ASP.NET 이 처리하는 모든 응답(404 포함)에 실림
  → ASP.NET 2.0(2005년) 이라는 정확한 런타임 버전 노출.
- **TRACE 는 광고만 되고 미구현(501)** — `Allow`/`Public` 헤더와 실제 동작 불일치.
- **HTTP/1.1 무-Host → `400` + `Server: Microsoft-HTTPAPI/2.0`** (HTTP.sys 계층 노출).

## A-6. 다음 단계 갱신

1. IIS/ASP.NET 타겟 스캔 기본 확장자 세트를 `.asp` + `.aspx/.ashx/.asmx/.ascx/.axd/.svc`
   로 확장(이번엔 결과 0 이었지만 **누락이 false negative 를 만드는 구조적 위험**이 확인됨).
2. `Host` 헤더 반사 + 내부 IP 노출(10.0.0.14) → 캐시 포이즈닝/호스트 헤더 인젝션 축 검증.
3. `X-AspNet-Version: 2.0.50727` → ASP.NET 2.0 알려진 취약점(ViewState MAC, Padding Oracle

4. `OPTIONS` 광고 ↔ TRACE 501 불일치는 하드닝 권고 항목으로 보고.
