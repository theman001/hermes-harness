# SQL Injection — 상한 실측과 판정 함정 (classic ASP / IIS / MSSQL)

> 승격 대상: `tech-docs/web/frameworks/iis-asp-mssql/sql-injection.md`
> **병합 주의**: 같은 대상군에서 나온 기존 초안 `_pending_review/<기존 project>/sql-injection.md`
> 가 이미 있다. 이 문서는 그 초안의 §2~7 케이스 중 일부를 **재확인**하고, **두 가지 판정을
> 정정·보강**한다(§3 UNION, §4 스택드). 승격 시 새 파일을 만들지 말고 그 문서에 케이스를 합칠 것.
> 이 초안은 대상 식별자(도메인/계정/비밀번호/엔드포인트 파일명)를 `<...>` placeholder 로 치환했다 —
> 병합 시 기존 문서의 표기 관례에 맞춰 정리하면 된다.

## 1. 원리 (기존 초안 §1 과 동일 — 요약)

문자열 결합 쿼리에서 공격자가 제어할 수 있는 층위는 셋이다:
**(1) 조건 제어**(WHERE 참/거짓 → 오라클), **(2) 값 제어**(INSERT/UPDATE 값 목록에 식),
**(3) 문장 제어**(`;` 로 추가 문장). 상한은 **드라이버의 다중 문장 허용 여부 + DB 계정 권한**이
결정하므로, "SQLi 있다"로 끝내지 말고 **항상 상한을 실측**한다.

이번 프로젝트의 상한: **조건 제어 + 값 제어 + 문장 제어 모두 가능**(= 임의 DML + 임의 T-SQL),
단 **OS 명령 실행은 불가**(계정이 `sysadmin`/`db_owner` 아님 + `xp_cmdshell`·OLE 비활성).

## 2. 케이스 — 인증 우회 (로그인 쿼리의 WHERE 절 조작)

로그인 쿼리가 `WHERE uname='<u>' AND upass='<p>'` 형태로 조립되면, 사용자명만 조작해도 인증된다.

```
u=admin'--        (뒤의 AND 절 주석 처리)      → 302 + 세션 발급
u=x' OR '1'='1'-- (조건식 자체를 참으로)
p=' OR '1'='1     (비밀번호 쪽만 조작)
```

**판정 함정**: 로그인 성공/실패가 **같은 200** 으로 오는 앱이 많다. 상태코드가 아니라
⑴ `Location` 헤더(302 → 내부 페이지) ⑵ **인증 후에만 생기는 UI 요소**(글쓰기 폼 등)로 판정한다.
실패 기준선(존재하지 않는 계정)을 반드시 같이 보내 대비한다.

★ **부수 효과가 진짜 위험**: 로그인 로직이 `Session("user") = Request.Form("u")` 처럼 **검증 없이
입력값을 세션 신원으로 저장**하면, 그 값이 이후 모든 페이지/쿼리에 흘러간다 → §6 second-order 로 연결.

## 3. ★★ UNION 가용성은 **앱 단위가 아니라 엔드포인트 단위**로 판정한다 (기존 초안 정정)

기존 초안은 "UNION 기반과 시간 지연 기반이 모두 막혔다"고 기록했지만, **같은 대상군·같은 앱에서
둘 다 성립했다.** 원인은 기법이 아니라 **엔드포인트와 페이로드 형태**였다.

**왜 어떤 엔드포인트는 UNION 이 안 되고 어떤 곳은 되나**

| 엔드포인트 유형 | UNION 성립 | 이유 |
|---|---|---|
| 같은 파라미터가 **컬럼 수가 다른 여러 쿼리**에 재사용(예: `SELECT a,b … WHERE id=` + `SELECT a,b,c,d … WHERE id=`) | ❌ | 한 페이로드로 모든 실행 쿼리의 컬럼 수를 맞출 수 없다(전부 500) |
| 파라미터가 **단일 쿼리**에만 쓰임 | ✅ | 컬럼 수만 소스에서 세면 된다 |

**페이로드 형태(핵심)**: 주입 지점이 문자열 리터럴 **안**, 그것도 **괄호 안**이면 열린 것을
정확히 닫고 나가야 한다. 그냥 `0 UNION SELECT …` 를 넣으면 앞의 따옴표/괄호가 안 닫혀 500 이다.

```
원본:  … AND (CHARINDEX(<col>, '<입력>') > 0 OR CHARINDEX(<col2>, '<입력>') > 0)
페이로드: q')>0) UNION ALL SELECT <정확히 n개 컬럼>--
```

**컬럼 수는 반드시 소스(또는 오류 메시지)에서 센다** — 추측 금지. 소스를 LFI 로 읽었다면
SELECT 목록을 그대로 세면 된다.

**성공 판정**: UNION 결과가 **응답 본문에 렌더**되는지 본문 마커로 확인한다(예: 2번째 컬럼에
`'ACU-MARKER'` 를 넣고 그 문자열이 페이지에 나오는지). 마커가 여러 컬럼에 걸쳐 나오면 "5/5 발견"
처럼 **컬럼 매핑까지 확인**한다.

**이게 왜 중요한가**: 성립하면 **요청 1건으로 임의 데이터가 화면에 출력**된다. 블라인드
이분탐색으로 같은 데이터를 뽑는 데 수백 요청이 걸렸다(이 프로젝트: 439 요청 → 수 요청).
보고서 재현성·속도·임팩트 서술이 전부 달라진다.

★ **일반 규칙**: 한 엔드포인트에서 UNION 이 500 이라고 **앱 전체 결론으로 승격하지 말 것**.
"이 엔드포인트에서는 불가" 로만 기록하고, 파라미터가 단일 쿼리에 쓰이는 **다른 엔드포인트를
찾아 재시도**한다(검색·상세 조회·리포트형 파라미터가 후보).

## 4. ★★ 스택드 쿼리 — 문자열 문맥 실패를 "불가"로 일반화하지 말 것 (기존 초안 정정)

기존 초안은 "다중 문장이 실행되지 않아" 로 상한을 고정했다. 이번 프로젝트에서는 **실행됐다.**

**시험 절차(차분 타이밍)**:

```
기준선        : id=<존재값>                        → 200, t=0.35s
문장 실행 참  : id=0;IF 1=1 WAITFOR DELAY '0:0:04'--  → 200, t=8.5s   ← 지연 = 문장 실행 증거
문장 실행 거짓: id=0;IF 1=2 WAITFOR DELAY '0:0:04'--  → 200, t=0.59s
```

★ **대조군(`IF 1=2`) 없이 "지연이 있네" 만 보면 안 된다** — 네트워크 지터/서버 부하와 구분 불가.
참/거짓 두 요청의 **차분**이 증거다.

**함정 1 — 주입 지점의 문맥을 먼저 본다**: 문자열 리터럴 안이면 `'` 를 먼저 닫아야 하는데,
닫는 과정에서 뒤 문법이 깨지면 500 이 뜬다. **숫자 문맥 파라미터(따옴표 불필요)에서 먼저 시험**하면
이 문제를 피할 수 있다. 이 프로젝트: 숫자 문맥(`id=0;…`)은 8.5s 지연 / 따옴표 문맥(`id=1';…`)은 500.
→ 후자만 보고 "불가"로 결론내면 **오판**이다.

**함정 2 — 앱이 같은 쿼리를 여러 번 실행하면 지연이 배수로 나온다**: 페이지가 같은 파라미터로
쿼리를 2회/3회 실행하면 `DELAY 4초` 가 8.5초/12초로 관측된다. 배수를 알면 **지연값 자체가
"쿼리가 몇 번 실행되는지"의 정보**가 된다(부수 관찰). 판정은 "차분 > 0" 이면 충분하다.

**함정 3 — 로그인 폼에서도 시험하라**: 인증 전에 실행되는 `WHERE` 절에서도 스택드가 되면
**인증 없이 임의 문장 실행**이다. 이 프로젝트는 로그인 파라미터에서도 4.37s 지연이 관측됐다.

## 5. ★★ 스택드를 **boolean 오라클로 전용** — 화면에 안 나오는 값을 읽는 법 (새 기법)

스택드가 되면 `IF <조건> WAITFOR DELAY` 로 **어떤 boolean 질의든 시간 오라클로 바꿀 수 있다.**
페이지에 렌더되지 않는 값(=권한, 객체 존재 여부, 교차 DB)을 **쓰기 없이** 읽는 데 쓴다.

```
id=0;IF (SELECT IS_MEMBER('db_datawriter'))=1 WAITFOR DELAY '0:0:04'--      → 권한
id=0;IF (SELECT IS_SRVROLEMEMBER('sysadmin'))=1 WAITFOR DELAY '0:0:04'--
id=0;IF (SELECT HAS_PERMS_BY_NAME('<t>','OBJECT','INSERT'))=1 WAITFOR DELAY '0:0:04'--
id=0;IF (SELECT HAS_PERMS_BY_NAME('<db>.<schema>.<t>','OBJECT','UPDATE'))=1 WAITFOR DELAY '0:0:04'--
```

**상한 판단에 바로 쓰는 체크리스트**(전부 읽기 전용, 쓰기 0건):

| 질의 | 의미 |
|---|---|
| `IS_SRVROLEMEMBER('sysadmin')` / `IS_MEMBER('db_owner')` | RCE/DDL 급 권한 여부 |
| `IS_MEMBER('db_datawriter')` / `db_datareader` | DML 가능성 |
| `HAS_PERMS_BY_NAME(<obj>,'OBJECT','INSERT'\|'UPDATE'\|'ALTER'\|'CONTROL')` | 객체 단위 권한 |
| `HAS_PERMS_BY_NAME(NULL,NULL,'ADMINISTER BULK OPERATIONS')` | 파일 읽기/쓰기(bulkadmin) |
| `IS_SRVROLEMEMBER('securityadmin')` | 권한 상승 여지 |
| `sys.databases` / 교차 DB 객체에 대한 `HAS_PERMS_BY_NAME` | **다른 앱 DB 까지 영향 범위**인가 |

★ **오라클만 믿고 "쓰기 가능"으로 보고하지 말 것** — 권한 TRUE ≠ 실제 INSERT 성공(트리거/제약/
권한 이외 차단). 보고서에는 **오라클 결과와 실제 실행 결과를 분리해서** 쓴다(§7).
★ 반대로, **실제 다른 앱 DB 에 쓰는 것은 대개 범위를 넘는다** — 권한만 확인하고 "실행은 하지
않음"을 명시하는 것이 정직한 상한 서술이다.

## 6. 케이스 — INSERT 값 목록 주입 + 스택드 결합, 그리고 **정상 경로가 상수로 고정한 열을 마커로 쓰기**

회원가입류 `INSERT INTO users (c1..cn) VALUES ('<u>','<p>','<e>','<r>','<a>')` 조립:

```
u = x','p','e','r','INJECTED') ; IF 1=1 WAITFOR DELAY '0:0:04'--
```

- 앞부분이 `'x','p','e','r','INJECTED'` 로 값 목록을 정상 종료시키고, `)` 로 문장을 닫은 뒤
  `; IF …` 로 **문장을 추가**한다. → **302 + 4.35초 지연** = 값 주입 + 문장 제어 동시 증명.

★★ **증명 마커 선정 규칙**: 그 폼의 **정상 경로가 상수로 고정하는 열**을 고르면, 그 열의 값이
바뀌는 것 자체가 "주입으로만 가능한 결과"가 된다. 이 프로젝트는 정상 등록이 프로필 이미지 열을
**항상 빈 문자열**로 넣었기 때문에, `'INJECTED'` 를 넣어두고 다시 읽어오면 **정상 경로로는 절대
불가능한 값**이 증거가 된다(대조군 행과 형태 비교가 자동으로 성립).

## 7. ★ 임의 DML 증명은 **정상 로그인까지 가야 완결**된다 (3단 프로토콜)

`200`/`302` 는 INSERT 성공을 증명하지 않는다. 순서대로:

1. **행 실존**: `(SELECT COUNT(*) FROM users WHERE uname='<주입이름>')>0` → UNION/오라클로 확인
2. **값 일치**: 삽입한 각 열을 다시 읽어 지정값과 비교(`upass`, 마커 열)
3. **★ 앱이 그 계정을 실제 계정으로 인정하는가**: **정상 로그인 폼**으로 로그인 →
   `302 Location: <내부페이지>` + 인증 후 UI 요소 확인

3번까지 가야 "DB 에 행이 생겼다"가 아니라 **"애플리케이션 계정이 생겼다"** 는 주장이 성립한다.
(권한 오라클이 `UPDATE` 도 TRUE 라면 기존 계정 비밀번호 변경 = 계정 탈취와 동등하지만,
**기존 행 변경은 하지 않는다** — 파괴성 회피 원칙. 능력은 기록하고 실행은 하지 않는다.)

**되돌림 불가 주의**: DELETE 권한이 없으면 테스트 행은 영구 잔존한다(이 프로젝트는 권한은 있었지만
기존 행 무변경 원칙 + 대상이 주기 리셋되는 데모라 리셋으로 소멸). 승인 요청에 반드시 적는다.

## 8. 케이스 — second-order (저장된 값이 **다른 문장**에서 재사용) + **상한의 정직한 표기**

**발견 조건**: 같은 값이 ⑴ 신원으로 저장되고 ⑵ **다른 SQL 문**의 값 목록에 다시 결합될 때.
이 프로젝트는 세션에 저장된 사용자명이 게시글 INSERT 의 작성자 열로 흘러가는데,
**그 열만 이스케이프 누락**(제목/본문은 `Replace(x,"'","''")` 적용, 작성자 열은 미적용)이었다.

★ **파일 단위·열 단위로 이스케이프 적용 여부를 감사하라** — "이 앱은 이스케이프한다"는 판정은
거의 항상 틀린다.

**증명과 함정**:
```
따옴표 포함 사용자명으로 우회 로그인 → 세션 인증됨 (302)
그 세션으로 게시글 POST → 500        ← 다른 문장이 깨졌다 = second-order 성립
대조군: 정상 계정으로 같은 POST → 200 + 게시글 생성
```

★★ **여기서 멈추고 "데이터 주입 가능"이라고 쓰면 과대주장이다.** 로그인 쿼리(=`WHERE u='<값>'`)를
통과하는 문자열과, INSERT 의 `VALUES (…)` 목록에서 문법을 유지하는 문자열은 **상호 배타적**이다:
인증을 통과한 값은 값 목록에서 반드시 구문 오류를 낸다. 그래서 실제 상한은
**"그 세션의 쓰기 기능 파괴(500)"** 이며, 이 프로젝트는 그렇게 기록했다.

**일반 규칙**: second-order 는 "증명됨"과 "이용 가능"이 다르다. ⑴ 저장 → ⑵ 다른 문장에서
깨지는 것까지 확인 → ⑶ **공격자가 원하는 값/구조를 실제로 만들 수 있는지**를 마지막에 판정한다.

## 9. 부적절한 판정 방법 경고 (오보 방지)

- `OBJECT_ID('xp_cmdshell')` / `OBJECT_ID('xp_dirtree')` / `OBJECT_ID('xp_fileexist')` 로
  확장 프로시저 존재를 조회하면 **NULL 이 나온다**(확장 프로시저는 `sys.objects` 에 그렇게
  등록되지 않는다). 이걸 "없음"으로 쓰면 **오보다.** → `sys.configurations` 의 `value_in_use`
  (예: `xp_cmdshell`), 실제 `EXEC` 시도, 오류 메시지로 확인하거나 **"판정 불가"** 로 명시한다.
- 권한과 실행을 **한 문장으로 뭉개지 말 것**: "INSERT 권한 TRUE" 와 "INSERT 실행 성공(행/로그인
  확인)" 은 별개 근거다. 보고서에 어느 쪽인지 명시한다.

## 10. 방어 관점 (기존 초안 §7 보강)

- 값 결합 금지 + **파라미터 바인딩**. 이스케이프는 값 목록/식 문맥에서 특히 무력하다.
- 최소 권한: 웹앱 계정에 `db_datareader/writer` 만 주고 **교차 DB 권한 제거**(이 프로젝트는 계정
  하나로 인접 앱 DB 까지 읽고 쓸 수 있었다).
- `xp_cmdshell`·OLE Automation·CLR 비활성 + `sysadmin` 금지(이 프로젝트는 이 조합이 RCE 를 막은
