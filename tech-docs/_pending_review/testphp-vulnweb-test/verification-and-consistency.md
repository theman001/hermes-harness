# 검증 방법론 — 판정·재현성·상한 (스택 무관)

> 승격 대상: `tech-docs/web/general/verification-and-consistency.md`
> **병합 주의**: 같은 대상군의 기존 초안 `_pending_review/<기존 project>/verification-and-consistency.md`
> 가 이미 있고(그 문서가 최우선 병합 대상), 이 문서는 **그 문서에 없는 6개 절(§1~§6)을
> 추가**한다. 새 파일을 만들지 말고 기존 문서에 병합할 것. 대상 식별자는 placeholder 로 치환했다.

기존 초안이 다룬 것(중복 서술하지 않음): ⑴ 대조군 필수 ⑵ 도구 기본 동작(리다이렉트 추적/이중
인코딩/POST 본문 소실) ⑶ 절대값이 아니라 대비로 판정 ⑷ 쓰기는 행 내용으로 검증 ⑸ 마감 시
일괄 재현 검증 ⑹ 산출물 수선은 백업+실패 보고 ⑺ 상한 판단도 실측.
**아래는 그 뒤에 새로 겪은 6가지다.**

## 1. ★★ "불가" 판정을 **앱 전체로 일반화**하지 말 것 — 오판의 발생 구조

실제 사고: 한 라운드에서 UNION 을 시도해 전부 500 을 받고 "UNION 불가" 로 결론 → 이후 라운드가
전부 블라인드 이분탐색(수백 요청)에 묶였다. 다음 phase 에서 **다른 엔드포인트 + 올바른 페이로드
형태**로 시도하니 성립했고, 이후 추출이 수 요청으로 줄었다.

**오판이 만들어진 구조**(일반화 가능한 패턴):
1. **한 엔드포인트에서 실패** → "이 앱은 UNION 이 막혀 있다" 로 기술(테스트 대상)을 승격.
   ⑴ 페이로드가 주입 지점의 문맥(괄호/따옴표/컬럼 수)을 맞추지 못한 것이 원인이었는데,
   ⑵ 결과만 보고 **기법 자체를 부정**했다.
2. 그 결론이 문서·HANDOFF 로 굳어 **다음 phase 의 전제**가 됐다(전제를 의심하지 않고 그 위에 쌓음).

**규칙**:
- 음성 결과는 **항상 "어디서(엔드포인트), 어떤 형태로(페이로드 원문) 시도했는지" 와 함께** 기록한다.
  이렇게 남기면 다음 사람이 "형태만 바꿔 재시도" 를 할 수 있다. 결과만 남기면 못 한다.
- **기법 부정 결론("UNION 불가", "스택드 불가")에는 재검증 트리거를 붙인다**: "이 엔드포인트에서
  불가" 로 한정하고, **다른 엔드포인트/다른 문맥에서 재시도**를 TODO 로 남긴다.
- 새 phase 를 시작할 때 **이전 phase 의 부정 결론 중 임팩트가 큰 것 1~2개를 재검증**한다(새 공격
  보다 ROI 가 높다 — 이미 "불가"라고 적힌 건 아무도 다시 안 본다).

## 2. ★★ 재현/검증 스크립트 **자체를 의심하라** — 스크립트도 틀린다

마감 단계에서 헤드라인 PoC 일괄 검증 스크립트(N체크)를 만들어 돌렸더니 1건이 FAIL 이었다.
대상이 바뀐 줄 알았으나 **스크립트 결함**이었다:

- 검사 항목: "`?RetURL=<외부 URL>` 로 GET 하면 302 + 외부 Location 이 나와야 한다"
- 실제 동작: 그 앱은 **로그인 POST 가 성공한 뒤에만** `redirect` 를 실행한다 → 자격증명 없는
  GET 으로는 리다이렉트가 발생하지 않는다(검사 설계 자체가 틀림).

**규칙**:
- **스크립트 FAIL 을 "대상 변화" 로 단정하지 말 것.** 그 체크에 **성공이 보장된 대조군 입력**을
  붙여 ⑴ 스크립트 로직이 맞는지 ⑵ 대상이 변했는지 를 분리한다.
- 검증 스크립트의 각 체크는 **"성공이 자명한 경우" 를 최소 1개 포함**해야 한다(스크립트
  자기검증). 전체 FAIL/전부 FAIL 이면 대상이 아니라 스크립트를 먼저 의심한다.
- FAIL 항목은 **고치기 전에 보고하지 않는다.** 이번엔 고쳐서 전항목 PASS 를 확인한 뒤 보고했다 —
  그대로 보고했다면 존재하지 않는 회귀를 주장할 뻔했다.
- 스크립트 원문과 실행 로그를 **project 폴더에 남긴다**(phase 로컬 캡처가 지워져도 재현 가능).

## 3. ★ "판정 불가" 를 음성 근거로 쓰지 말 것 — 방법이 틀린 조회

권한/기능 존재를 확인하려고 `OBJECT_ID('<확장 프로시저>')` 류 조회를 썼는데 전부 NULL 이 나왔다.
그 값만 보면 "그 기능은 없다" 로 쓸 수 있지만, **그 방식으로는 존재 자체를 판정할 수 없다**
(확장 프로시저는 `sys.objects` 에 그렇게 등록되지 않는다). 조회 결과가 NULL 이라는 사실은
**"없다" 가 아니라 "이 방법으로는 모른다"** 였다.

**규칙**: 판정 방법의 **타당성을 먼저 검증**한다 — ⑴ 그 방법으로 **양성 대조군**(존재하는 것으로
아는 항목)도 TRUE 가 나오는지 확인하고, ⑵ 안 나오면 방법을 바꾸거나 **"판정 불가"** 로 명시한다.
"판정 불가" 를 "없음" 으로 쓰면 조용한 오보가 된다(보고서에서 음성 근거를 인용하는 순간 확정된다).

## 4. ★ 리셋형 대상에서 증거·재현성 관리 (시점 분리)

대상이 주기적으로 콘텐츠를 초기화하는 유형이면:

- **리셋을 관찰했으면 시각과 함께 기록**한다(이번: 행 수가 수 분 사이 급감 → 리셋 직후였음).
  리셋 직전에 캡처한 증거와 직후 결과가 다르면 **"취약점 소실"이 아니라 "증거 데이터 소실"** 이다.
- 쓰기 PoC 의 증거는 **① 실행 시점의 요청/응답 원문 ② 그 시점의 행 수/존재 확인** 을 짝으로
  남긴다. 이후 라이브에서 사라져도 "재현 시 동일 결과" 를 주장할 근거가 된다.
- **재현 절차에 "데이터를 다시 만들어라" 단계를 명시**한다(존재하는 id/행을 하드코딩하지 않는다).
- 하루를 넘겨 작업할 때: **이전 라운드의 행 수·계정·게시글을 전제로 한 PoC 는 자동으로 깨진다.**
  각 라운드 시작 시 개수/존재를 다시 확인하는 1요청을 넣는다(비용 1, 이득 큼).
- 검증 스크립트는 **쓰기를 포함하지 않는 형태**로 만든다 — 리셋형 대상에서 매번 재실행 가능한
  유일한 검증이 된다(이번: 24체크 전부 읽기 전용).

## 5. 삭제·파괴 경로를 **쓰기 전에** 읽기 전용으로 판정하라

이 대상 앱에는 **애플리케이션 자체 로직**으로 "카운트가 임계값을 넘으면 해당 게시판의 글을
일괄 DELETE" 하는 분기가 있었다(`if rs.fields("total") > 100 then DELETE FROM … WHERE forumid=` +
파라미터를 **문자열 결합**). 즉 ⑴ 쓰기 승인을 받아 POST 를 하다가 ⑵ 그 파라미터를 주입하면
⑶ 서드파티 데이터가 삭제된다.

**규칙**:
- 상태 변경(POST/쓰기)을 승인받았더라도, **그 요청의 파라미터에 주입 페이로드를 넣지 않는다**
  (주입은 조회(GET)계 파라미터에서만). 쓰기 경로의 주입은 별도 승인 사안이다.
- 쓰기 전에 **소스(LFI 등)로 삭제 분기의 도달 조건을 확인**하고, 도달 가능하면 승인 요청서에
  "이 분기에 도달하지 않도록 파라미터를 고정한다" 를 명시한다.
- 삭제 권한이 없으면 **테스트 데이터는 정리 불가**임을 승인 요청·보고서에 적는다.

## 6. 상한(ceiling) 서술의 3단 구분 — "확인/실행/미실행" 을 섞지 말 것

상한을 보고할 때 근거의 **종류**를 구분해 적는다(이번 project 에서 실제로 쓴 틀):

| 표기 | 뜻 | 예 |
|---|---|---|
| **실행 확인** | 공격을 수행해 결과를 관측했다 | 임의 행 INSERT → 정상 로그인 성공 |
| **권한만 확인(실행 안 함)** | 읽기 전용 오라클로 가능성만 확인 | 인접 앱 DB 에 `UPDATE` 권한 TRUE |
| **판정 불가** | 방법이 부적절했거나 데이터 부족 | 확장 프로시저 존재 여부 |

"권한만 확인" 을 "실행 확인" 처럼 쓰면 과대주장이 되고, 반대로 "판정 불가" 를 "불가" 로 쓰면
과소주장이 된다. 둘 다 보고서 신뢰도를 깎는다.
