# Stored XSS (게시판 저장형) — 재확인 + 필터·영향범위 판정

> 승격 대상: `tech-docs/web/frameworks/iis-asp-mssql/stored-xss.md`
> **병합 주의**: 같은 대상군의 기존 초안 `_pending_review/<기존 project>/stored-xss.md` 에
> 원리·CDP 실행 프루프·리셋 대응이 이미 있다. 이 문서는 **재확인 사례 + 필터 판정(§2)·영향범위
> 판정(§3)** 을 추가한다. 새 파일 금지, 기존 문서에 병합.

## 1. 재확인된 사례

이번 project (Round 8) — 독립 phase 에서 같은 결론. phase 1 에서는 쓰기
미승인으로 **미실증**이었고, phase 2 에서 재승인을 받아 실증했다(승인 흐름 자체가 병목이었다는
기록도 함께 남긴다 — 처음 거부된 항목은 **사유가 바뀌면 재요청할 가치가 있다**).

## 2. ★ 필터는 "무엇을 막는지" 목록을 먼저 소스에서 읽어라

이 앱의 게시글 입력 필터는 **문자열 하나만** 검사했다:

```
If InStr(1, Request.Form("<text>"), "<a href=") > 0 then Response.End
```

→ `<script>`, `<img src=x onerror=…>`, `<svg onload=…>` 는 **전부 통과**했다. 저장 시 처리도
따옴표 이스케이프(`Replace(x,"'","''")`)뿐이고 **HTML 인코딩은 없었다**(SQL 안전 ≠ XSS 안전).

**규칙**: ⑴ 필터가 있으면 **검사 대상 문자열 목록**을 그대로 인용해 기록하고(그 자체가 우회
근거), ⑵ "막을 수 있는 최소 집합" 을 뒤집어 **다른 태그/이벤트 핸들러**로 재시도한다.
⑶ 필터가 `on…=` 속성까지 검사하면 다른 컨텍스트(`<svg>`, `<body onload>`, `javascript:` URL,
`<iframe srcdoc>`)를 시도한다. ⑷ 차단 문자열이 1개뿐인 필터는 **취약점이 아니라 힌트**다.

## 3. ★ 영향 범위는 "누가 그 페이지를 여는가" 로 확정한다 (이번 phase 의 핵심 판정)

- 저장 후 **쿠키 없는 비인증 요청**으로 같은 페이지를 다시 요청 → **동일하게 렌더**됐다.
  → 영향 범위가 로그인 사용자에 국한되지 않고 **그 페이지를 여는 모든 방문자**다(공개 게시판은
  검색엔진/크롤러/비로그인 방문자까지 포함).
- **실행을 막는 장치가 없다는 것도 확인**해야 한다: 응답 헤더에 CSP 없음 + 세션 쿠키에 `HttpOnly`
  없음 → ⑴ 스크립트 실행 억제 없음 ⑵ `document.cookie` 로 세션 토큰 판독 가능(세션 하이재킹 체인).

**증거 등급 정직성(중요)**: 이번 phase 의 증거는 **서버 응답 본문에 페이로드가 무인코딩으로
포함됨**(curl, 비인증 재확인) 까지다. 기존 초안 §2 가 요구하는 **브라우저 실행 프루프(CDP +
`dialog_count`/`document.cookie`) 는 캡처하지 않았다** — 이 사실을 그대로 적는다. 렌더 증거를
"실행 확인" 이라고 쓰면 과대주장이고, 브라우저가 없는 환경이라면 그 한계를 명시하는 편이
신뢰도가 높다(재현 절차에 CDP 단계를 남겨 다음 실행에서 보강).

## 4. 게시글 작성 = 상태 변경 → 승인 흐름 (재확인)

- 게시 전에 **삭제 분기**(카운트 임계값 초과 시 일괄 DELETE)의 도달 가능성을 읽기 전용 오라클로
  확인하고, 승인 요청서에 "도달하지 않도록 파라미터를 고정한다" 를 명시한다.
- 되돌리기 불가(삭제 권한 없음)와 리셋 가능성을 함께 적는다 — 이 대상은 주기 리셋으로 실증 글과
  계정이 라이브에서 사라졌고, **증거는 캡처 시점 원문만 유효**했다.
- 흔적 최소화: 게시 1건 + 계정 1건. 기존 행 수정/삭제 0건.
