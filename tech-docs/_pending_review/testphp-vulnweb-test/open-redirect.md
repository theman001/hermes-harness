# Open Redirect — 재확인 + "인증 후에만 실행되는" 리다이렉트

> 승격 대상: `tech-docs/web/frameworks/iis-asp-mssql/open-redirect.md`
> (또는 `tech-docs/web/general/open-redirect.md` — 기존 초안 `_pending_review/<기존 project>/`
> 의 동명 문서와 병합 판단은 Claude Code 몫). 이 문서는 **재확인 + 3개 추가 관측**만 담는다.
> 새 파일 금지, 기존 문서에 병합.

## 1. 재확인된 사례

이번 project (Round 4·9, Round 12 재검증) — 외부 URL 을 담는 `Redirect`
파라미터가 원 상태코드/`Location` 헤더 검사로 그대로 재현됐다(24체크 검증에서도 PASS).

## 2. ★ 리다이렉트가 **인증 성공 후에만** 실행되는 경로가 있다 (체이닝 필요)

이 앱의 로그인 페이지는 자격증명이 맞아 `redirect` 를 실행하는 분기에 도달해야만 외부 이동이
일어난다. 그래서 **자격증명 없는 GET 으로는 검증되지 않는다**:

```
GET  /login?RetURL=http://<외부>/          → 리다이렉트 없음(폼 재렌더)   ← 여기서 "불가" 로 오진하기 쉽다
POST /login?RetURL=http://<외부>/  (우회 자격증명) → 302 Location: http://<외부>/
```

**함정**: ⑴ `curl -L` 을 쓰면 리다이렉트를 따라가 **200** 이 보여 "리다이렉트 없음" 으로 오판한다
(항상 `-L` 없이 + `Location` 헤더로 판정). ⑵ 인증 게이트가 걸린 리다이렉트는 **인증 우회 취약점과
한 요청으로 체이닝**해야 관측된다 — 그 자체가 "무자격 상태에서 임의 외부 이동" 체인이 된다.
⑶ 로그아웃 등 인증 불요 경로에 같은 파라미터가 있으면 그쪽으로도 재현된다(앱 전역일 가능성 →
같은 파라미터명을 모든 진입점에서 시도).

## 3. 검증 규칙 우회: 프로토콜 상대 URL

```
RetURL=http://<외부>/     → 통과
RetURL=//<외부>/          → 통과 (프로토콜 상대 URL, "http" 만 검사하는 화이트리스트를 우회)
```

**규칙**: 허용 목록 검사가 있는지 판단할 때 ⑴ `//host`, ⑵ `https:` vs `http:` 혼용,
⑶ `\`·탭·제어문자 삽입, ⑷ 자체 도메인으로 시작하되 다른 호스트로 이어지는 형태
(`https://<자기호스트>.attacker.tld`) 를 각각 시도한다. 통과/차단을 **형태별로 표로** 남긴다.

## 4. CRLF/헤더 인젝션으로 확장되는가 (음성 재확인)

`Redirect` 파라미터에 `%0D%0A` + 임의 헤더를 넣어도 **ASP 가 개행을 다시 인코딩**해 응답 헤더가
오염되지 않았다(음성). → 리다이렉트 취약점을 **헤더 인젝션/응답 분할로 승격하지 말 것**.
음성 판정을 보고할 때는 대조군(정상 URL)이 302 를 냈다는 사실과 함께 적는다(형식 자체가 유효했다는 근거).

## 5. 임팩트 서술

단독으로는 "사용자를 외부로 이동" 수준이지만, ⑴ 인증 게이트를 우회 자격증명으로 통과시키는
체인과 결합하면 **피싱/세션 리다이렉트 구성**이 되고, ⑵ 같은 호스트에 XSS 가 있으면
`javascript:` 류 시도(대개 현대 브라우저에서 무효)보다 **외부 리다이렉트 + 탈취 페이지**가
현실적인 악용이다. 어느 쪽이든 **검증한 범위까지만** 서술한다.
