# Path Traversal (Arbitrary File Read) — 재확인 + 경로 해석 규칙

> 승격 대상: `tech-docs/web/frameworks/iis-asp-mssql/path-traversal.md`
> **병합 주의**: 같은 대상군의 기존 초안 `_pending_review/<기존 project>/path-traversal.md`
> 에 대부분의 내용(인코딩 규칙·대조군 프로토콜·우선순위 표)이 이미 있다. 이 문서는 **재확인
> 사례 1줄 + 새로 관측한 경로 해석 규칙(§2)** 만 추가한다. 새 파일 금지, 기존 문서에 병합.

## 1. 재확인된 사례

이번 project (Round 4~5, Round 7 재확인) — 독립 phase 에서 같은 결론:

- 인코딩 **없는 평문 `../`** 만 통했다. `..%2f`, `%2e%2e%2f`, `..%5c`, `..%252f`, `%00` 삽입은
  전부 500(= 기존 초안 §3 의 "정확히 한 번만 인코딩" 규칙과 동일 결론. 이번엔 인코딩이 아예 불필요).
- 대조군 프로토콜(기존 초안 §4)이 유효했다 — 음성 후보를 판정할 때마다 성공이 보장된 입력을 같이 보냈다.
- `include`/파일읽기 기반 코드에서 traversal = **소스 유출**이라는 통찰(기존 초안 §1)이 그대로 성립:
  앱 소스 11개 + 설정 파일을 확보한 뒤 모든 후속 공격이 화이트박스로 바뀌었다.

## 2. 새로 관측: **"웹루트 기준" 경로와 "부모 기준" 경로를 구분하라** (기존 초안 §5 보강)

기존 초안 §5 는 "절대경로 → 상대경로 변환" 규칙(`C:\app\x.asp` → `../../../../app/x.asp`)을
다룬다. 여기에 **한 가지 실패 패턴**을 추가한다:

```
../<루트의 파일>              → 500   (부모로 나가면 웹루트 밖이라 실패)
<하위디렉터리>/../<루트의 파일> → 200   (웹루트에서 시작해 되돌아오면 성공)
```

즉 이 앱은 입력을 **웹루트 기준 상대경로**로 해석했다. `..` 를 아무리 많이 붙여도 부모 방향
탐색은 그 지점에서 실패하고, **루트 파일을 읽으려면 루트에서 역참조해야** 한다.

**규칙**: ⑴ 먼저 **정상 include 경로**(예: `item=<존재하는 하위디렉터리>/<파일>`)가 200 인지로
경로 기준점을 확정한다. ⑵ 루트 소속 파일은 `<any-dir>/../<file>` 형태로, ⑶ 웹루트 밖 파일은
`../../(반복)/<abs-path>` 형태로 시도한다. ⑷ 두 규칙을 **섞으면** "차단됨" 처럼 보이는 500 이
뜬다 — 차단으로 오진하지 말고 기준점을 먼저 확정할 것.

**깊이 함정 재확인**: 기존 초안의 "`..` 를 넉넉히" 는 웹루트 밖 파일에 유효하다(초과분 무시).
단 위 ⑵ 규칙(루트 기준)과는 다른 방향이므로 **두 시도를 분리해서** 기록한다.

## 3. 무엇이 남았고 무엇이 막혔는지 (정보노출 ≠ 파일탈취)

- 읽힌 것: OS 설정/시스템 파일, 앱 루트의 `.asp` 소스 전부, `web.config`.
- 안 읽힌 것(전부 500, 대조군 200): 앱이 쓰는 로그 파일, 백업(`.bak`), `global.asa`,
  부트 설정, IIS `applicationHost.config`, 웹루트 하위 `web.config`.
  → **경로가 노출되어도 파일 탈취는 별개 finding** 이라는 기존 초안 §5 의 결론과 일치.
- **소스 유출의 파급**: 소스 안의 DB 접속 문자열을 얻어 SQLi 계정명과 **교차검증**했다
  (SQLi 로 읽은 `SYSTEM_USER` == 접속 문자열의 `Uid`). 교차검증은 "유출이 진짜"라는 강한 증거다.
- ★ **자격증명 탈취 ≠ 외부 DB 접속**: 접속 문자열의 서버가 `(local)\<인스턴스>` 형태면
  네트워크 도달성이 없어 **자격증명 자체는 재사용 불가**하다. 보고서에 "자격증명 노출"과
  "외부에서 DB 접속" 을 분리해 적는다(후자는 검증하지 않았다면 미검증으로).
