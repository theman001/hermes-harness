# Stored XSS (게시판 저장형)

> 승격 대상: `tech-docs/web/frameworks/iis-asp-mssql/stored-xss.md`

## 1. 원리

입력을 저장한 뒤 **출력 시 이스케이프하지 않고** 렌더링하면(ASP 고전에서는
`Response.Write(Request.Form("x"))`), 그 페이지를 여는 모든 사용자의 브라우저에서 스크립트가
실행된다. 반사형과 달리 **URL 을 보낼 필요가 없어** 피해자 유도가 쉽다.

**임팩트는 "alert 가 떴다"가 아니라 "무엇을 할 수 있는가"로 확정한다**: 세션 쿠키 판독 가능
여부(`document.cookie`, `HttpOnly` 부재), CSRF 토큰 탈취, 세션 하이재킹 체인.

## 2. 실행 절차

1. **쓰기 지점 찾기**: 게시글/댓글/프로필 같은 저장 경로를 찾는다. 폼 필드명은 소스(LFI 로
   확보한 `.asp`)나 요청 캡처에서 정확히 확인한다.
2. **최소 페이로드로 저장**: `<img src=x onerror=alert(1)>`
3. **실제 브라우저로 방문**해 실행을 확인한다(`browser` toolset + CDP).
   ★ `curl` 로 응답 본문에 태그가 있는 것만으로는 **실행 증거가 아니다** — 저장/리플렉션 구분도
   안 되고 브라우저 컨텍스트도 안 보인다.
4. **세션 영향 확인**: `document.cookie` 판독 가능 여부, 쿠키에 `HttpOnly` 가 붙어 있는지.
   실측 예: `dialog_count:1`, alert 텍스트, `cookie_readable:true`, `HttpOnly` 없음 → 세션
   하이재킹 체인 성립.

```python
# CDP 로 실행 프루프를 뜨는 골격 (alert 가로채기 + 쿠키 판독)
# page.on("dialog") 로 카운트/메시지 수집, js("document.cookie") 로 판독
# 결과를 텍스트로 저장 + 스크린샷 → 증거 파일로 보존
```

## 3. ★ 이 프로젝트의 교훈 — 저장형 PoC 는 서버에 남지 않는다

대상이 **인터넷에 공개된 데모 사이트**여서 주기적으로 **DB 가 리셋**됐고, 라운드에서 저장한
페이로드가 서버에서 사라졌다(같은 시기에 이전 라운드에서 만든 게시글도 함께 소실됨).

**그래서**:
- 저장형 취약점의 **유일한 증거는 실행 시점에 캡처한 원시 자료**(응답 본문, CDP 실행 프루프,
  스크린샷)다. 스크린샷·CDP 로그를 **반드시 별도 파일로 보존**한다.
- 보고서의 재현 절차에는 "**게시글을 다시 만들어라**"는 단계가 필수다(존재하는 게시글 id 를
  하드코딩하지 말 것 — 리셋되면 id 가 바뀐다).
- "지금 서버에 없다"를 "재현 불가"로 쓰면 안 된다. **취약점은 그대로이고 증거 데이터만 사라진
  것**이므로, 재실행 시 동일 결과가 나옴을 함께 서술한다.

## 4. 쓰기 승인이 필요한 이유

게시글 작성은 **상태 변경**이다. 승인 흐름에 따라 사전 승인을 받고, 다음을 지킨다:
- 가능하면 **자기 자신이 만든 콘텐츠**를 대상으로 한다(다른 사용자 글 수정/삭제 금지).
- 삭제 분기가 있는 앱(예: 카운트가 임계값을 넘으면 전체 삭제)이라면, 쓰기 전에 그 분기 도달
  가능성을 **읽기 전용 오라클로 먼저 판정**한다. 이 프로젝트에서는 카운트 쿼리의 `FROM` 이
  고정되어 임계값에 **구조적으로 도달 불가**임을 SQLi 오라클로 증명하고 진행했다(그 증명이
  안전성 근거로 보고서에 실렸다).
- 삭제 권한이 없으면 **정리 불가**임을 승인 요청에 명시한다.

## 5. 방어 관점

- 출력 컨텍스트에 맞는 이스케이프(HTML entity) + 입력 검증은 보조 수단으로만.
- 세션 쿠키에 `HttpOnly`(이 프로젝트는 **없어서** 하이재킹 체인이 성립), `Secure`, `SameSite`.
- CSP 로 인라인/외부 스크립트 제한.
