# 검증 방법론 — 오라클·대조군·재현성 (스택 무관)

> 승격 대상: `tech-docs/web/general/verification-and-consistency.md`
> **이 문서가 이 프로젝트에서 가장 재사용 가치가 높다** — 특정 취약점 기법이 아니라
> "판정 자체를 신뢰할 수 있게 만드는 규칙"이기 때문.

## 0. 왜 필요한가

취약점 보고의 가치는 **재현 가능성**에서 나온다. 그런데 잘못된 도구 기본값 하나, 인코딩 한 번,
변동하는 값을 하드코딩한 것 하나로 **판정이 조용히 뒤집힌다.** 아래는 이 프로젝트에서 실제로
오판 직전까지 간 사례와 그 규칙이다.

## 1. 판정에는 항상 **대조군**을 동봉한다 ★★

음성 결과("막혔다/없다")는 **요청 형식이 서버에서 통했다는 증거가 있을 때만** 유효하다.

```bash
# 형식 검증용 대조군(성공이 보장된 입력) + 실험군을 같은 형식으로 함께 보낸다
대조군: <알려진 성공 입력>       → 200   (형식 OK)
실험군: <관심 입력>              → 500   (형식 OK 인데 실패 = 진짜 차단/부재)
```

**대조군이 실패하면 실험군 결과는 버린다.** 실제 사고: LFI 스크립트가 이중 인코딩으로 전부 500
을 반환했는데, 대조군 덕분에 "백업 파일 탈취 불가"라는 **거짓 결론을 회피**했다.

## 2. 라이브러리/도구의 **기본 동작**을 의심한다 ★★

| 함정 | 증상 | 교정 |
|---|---|---|
| **자동 리다이렉트 추적**(`curl -L`, `urllib` 기본 opener) | 302 를 따라가 **200** 이 보임 → "리다이렉트 없음"으로 오판. 외부 도메인 추적 시 DNS 실패로 스크립트 중단 | 리다이렉트를 따라가지 않는 opener / `curl` 은 `-L` 없이. **원 상태코드 + `Location` 헤더**로 판정 |
| **이중 인코딩**(`%2f` 를 미리 넣고 `quote()` 재적용 → `%252f`) | 전부 500 → "차단됨"으로 오판 | 실제 문자(`../..`)를 조립한 뒤 **마지막에 한 번만** 인코딩 |
| **POST 본문 소실**(`-X POST -G` 조합) | IIS 가 411/빈 본문 반환 | POST 는 `-G` 없이, `--data-urlencode` 로 분리 |
| **표시상 성공 ≠ 실제 성공** | 등록/저장이 302·200 인데 반영 안 됨(세션 만료 등) | **저장 후 다시 읽어** 확인(§4) |

## 3. **참/거짓은 절대값이 아니라 대비로** 판정한다 ★

변동하는 값(행 수, id, 총계)을 PoC 에 하드코딩하면 대상이 변하는 순간 거짓이 된다.
공개 데모·운영 중 서비스는 다른 사용자와 리셋으로 **계속 변한다**(이 프로젝트: 오라클 TRUE 응답
행수가 라운드 사이에 21 → 114 로 변했고, 이전 라운드에서 만든 게시글 id 가 소멸했다).

```
NG :  TRUE 이면 21 행이 나온다
OK :  FALSE(0행) 와 구분되면 TRUE 다          ← 판정식
OK :  id 는 매번 목록 페이지에서 새로 추출한다  ← 의존값 자동 발견
```

**의존값 자동 발견 단계를 PoC 에 넣는다**:
```bash
TID=$(curl -s "$BASE/forum.asp?id=1" | grep -o "thread\.asp?id=[0-9]*" | head -1 | grep -o "[0-9]*$")
```

## 4. 쓰기 동작은 **응답 코드가 아니라 "행의 내용"으로** 검증한다 ★

`INSERT` 가 실행됐는지는 200/302 로 알 수 없다. **쓰기 → 읽기 왕복**으로 증명한다:

1. **기준선**: 정상 값으로 1건 등록해 기능이 동작함을 확립.
2. **대조군**: 페이로드 없이 등록해 **정상 행의 형태**를 기록.
3. **샘플**: 주입해 등록.
4. **판정**: 삽입 행의 각 열을 다시 읽어 지정값/서브쿼리 결과와 비교하고, 대조군 행과
   **형태가 다른지** 확인.
5. **상한·정리 가능성**: 스택드 쿼리 여부, 되돌릴 수 있는지(DELETE 권한)를 함께 확정하고
   승인 요청·보고서에 명시.

## 5. 헤드라인 PoC **일괄 재현 검증**을 마감 단계에 넣는다 ★

보고서를 쓰기 전에, 지금까지의 헤드라인 PoC 를 **같은 시점에 전부 다시 실행**한다:

- 취약점이 아직 유효한가
- **하드코딩된 값/id 가 아직 유효한가**(§3)
- 증거 파일 크기가 초기와 동일한가(파일 읽기형은 크기까지 같으면 안정적 증거)

```
LFI 4종        200 / 2,908B · 2,739B · 3,138B · 7,052B   ← 초기 라운드와 동일 크기 ✅
boolean-blind  (1=1) 다수행 / (1=2) 0행                 ✅
id SQLi        現存 id 에서 200/500                       ✅
리다이렉트      302 → 외부 URL                            ✅
저장형 XSS     서버측 소실(리셋) → 재작성 필요             ⚠
```

결과를 **재현성 검증 이력**으로 보고서 부록에 남긴다. "서버측 데이터만 사라진 경우"는 **재현
불가가 아니라 재실행 시 동일 결과가 나오는 항목**으로 구분해 서술한다.

## 6. 산출물 수선은 **백업 + 실패 보고**로 한다

문서 일괄 치환은 조용히 실패하기 쉽다. 스크립트로 할 때:
1. 대상 파일을 백업 폴더에 복사한다.
2. 치환 대상 문자열이 없으면 **실패로 보고**하게 만든다(무시하고 넘어가지 않게).
3. 몇 곳이 바뀌었는지 출력해 로그로 남긴다.

## 7. 상한(ceiling) 판단도 실측한다

"RCE 될 것 같다/안 될 것 같다"는 판단은 가치가 없다. 읽기 전용 질의로 **권한과 설정을 실제로
확인**해 근거를 남긴다(서버 역할 멤버십, 각 기능의 활성화 값, 저장 프로시저 실행 권한 등).
전부 FALSE 로 닫히면 시간낭비를 끊고 다른 축으로 이동한다.
