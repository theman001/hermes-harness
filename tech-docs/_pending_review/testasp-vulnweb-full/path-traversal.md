# Path Traversal (Arbitrary File Read)

> 승격 대상: `tech-docs/web/frameworks/iis-asp-mssql/path-traversal.md`
> (ASP `Server.MapPath` + `OpenTextFile` 조합에서 실측. §1 원리는 스택 무관.)

## 1. 원리

`Server.MapPath(".") & "\" & <입력>` 처럼 **웹루트 기준 상대경로에 입력을 이어붙여** 파일을 열면,
`../` 로 웹루트 밖으로 탈출할 수 있다. 이 프로젝트에서는 **필터가 전혀 없었다** — 즉 필터가
없다고 확인되면 이후 공격은 "우회"가 아니라 "경로 맞히기" 문제가 된다.

**핵심 통찰**: `include`/파일읽기 기반 코드에서 traversal 은 곧 **소스코드 유출**이다.
`.asp` 소스를 읽을 수 있으면 이후 모든 취약점이 **정적 분석으로 확정 가능**해진다(블랙박스 추측 →
화이트박스 확정). 그래서 traversal 발견 시 **가장 먼저 자기 자신(앱 소스)과 설정 파일**을 읽는다.

## 2. 케이스 A — 인코딩 없는 기본 traversal

```
GET /Templatize.asp?item=../../../../windows/win.ini        → 200 (2,739B)
```

★ **깊이 맞히기**: `..` 개수가 부족하면 "파일 부재"로 보이는 500 이 떠서 **차단으로 오진**하기
쉽다. 웹루트의 절대 깊이를 모를 때는 `..` 를 **넉넉히** 넣는다(초과분은 무시된다).

## 3. 케이스 B — 인코딩 규칙: **정확히 한 번만** 인코딩 ★★

가장 많이 시간을 태운 함정이다. 순서를 지킬 것:

1. 인코딩이 **없는** 경로로 먼저 시도한다(`../../../../windows/win.ini`). 이게 되면 인코딩은
   아예 필요 없다 — 인코딩을 먼저 넣으면 오히려 `%2f` 가 **문자 그대로** 취급된다.
2. 서버가 `%2f` 를 요구하는 경우에도 **실제 문자 `../..` 를 조립한 뒤 마지막에 한 번만** 인코딩한다.
   ```
   OK :  url = base + quote("../../../../windows/win.ini")      →  ../..  →  %2f
   NG :  url = base + quote("..%2f..%2f..%2f..%2fwindows%2fwin.ini")  →  %252f  (이중 인코딩)
   ```
   `%2f` 를 미리 넣고 `quote()` 를 다시 적용하면 `%252f` 가 되어 **전부 500** 이 뜬다.
   → 이 상태를 "차단됨"으로 읽으면 **오판**이다. 반드시 **대조군**으로 확인한다(§4).

## 4. 대조군 프로토콜 (필수) ★

음성 판정("파일을 못 읽었다")은 **요청 형식 자체가 서버에서 통했을 때만** 의미가 있다.
매 시도에 **성공이 보장된 대조군**을 같은 형식으로 함께 보낸다:

```
대조군: item=..%2F..%2FWindows%2Fwin.ini        → 200/2739  (형식 OK 확인)
실험군: item=<관심 경로>                        → 500       (형식 OK 인데 실패 = 진짜 차단/부재)
```

대조군이 실패하면 **실험군 결과는 버린다.** 이 프로젝트의 실제 사고: 2차 시도가 이중 인코딩으로
전부 500 이었는데, 대조군이 없었으면 "백업 파일 탈취 불가"라는 **결론 자체가 틀릴 뻔했다**.

## 5. 절대경로 → 상대경로 변환 (다른 소스에서 얻은 경로를 LFI 로 읽기)

DB 오류/백업 메타데이터 등에서 **절대경로**(`C:\Backup_x\y\z`, `C:\inetpub\wwwroot\app\db.asp`)를
얻었을 때 웹루트 기준 상대경로로 바꾸는 규칙:

1. 드라이브 문자 제거 (`C:\` → ``)
2. `\` → `/`
3. 앞에 `../..` 를 **넉넉히** 붙인다 (웹루트 깊이보다 많이)

```
C:\app\db.asp           →  ../../../../app/db.asp
C:\Backup_x\y\db.bak    →  ../../../../../Backup_x/y/db.bak
```

SQL Server 계열이면 `InstanceDefaultDataPath`/`BackupPath`/`msdb.dbo.backupset.physical_device_name`
으로 실제 경로를 먼저 얻어두면 추측이 줄어든다. **단, 그 계정 권한 밖이면 차단된다** — 이
프로젝트에서는 백업 경로는 알아냈지만 23/23 경로가 읽히지 않아(대조군 200) "경로 노출은 성립,
파일 탈취는 불가"로 분리 기록했다. **정보노출과 파일탈취는 별개 finding 이다.**

## 6. 무엇을 읽을 것인가 (우선순위)

| 순위 | 대상 | 이유 |
|---|---|---|
| 1 | **앱 자신의 소스**(각 `.asp`) | SQL 결합/인증/리다이렉트를 화이트박스로 확정 → 이후 라운드의 방향이 결정됨 |
| 2 | 설정 파일(`web.config`) | **DB 접속문자열**(host/DB/user/pass) → SQLi 확장 |
| 3 | `db.asp`/`conn*.asp` 같은 연결 스크립트 | 접속 문자열이 하드코딩된 경우가 많음 |
| 4 | OS 파일(`win.ini`, `unattend.xml`) | 버전·호스트명·평문 관리자 암호(오토로깅) 단서 |
| 5 | 백업/덤프 파일 | 있으면 최대 임팩트지만 대개 권한/경로 문제로 실패 |

ASP 소스 안에서 grep 할 키워드: `Provider=`, `Pwd=`, `Password`, `Response.Redirect`,
`Request.QueryString`, `Replace(`, `INSERT INTO`, `OpenTextFile`.

## 7. 방어 관점

- 사용자 입력을 경로에 결합하지 않는다(파일명 화이트리스트/ID 매핑).
- 정규화 후 **베이스 디렉터리 prefix 검사**(`Path.GetFullPath` 후 `StartsWith`).
- `.asp` 소스와 설정 파일을 웹루트 밖에 두고, 웹루트 밖 파일은 서비스 계정 권한으로도 접근
  최소화한다. (이 프로젝트에서는 `C:\Windows` 방향과 웹루트 밖 앱 폴더가 모두 열려 있었다.)
