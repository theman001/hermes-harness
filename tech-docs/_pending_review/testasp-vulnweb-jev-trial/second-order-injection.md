# Second-Order SQL Injection (저장된 값을 다시 SQL 로 쓸 때)

> 이 파일은 동일 대상의 기존 초안에 **없던 기법**이다 → 새 문서로 승격 검토.

## 1. 원리

1차 입력이 SQL 로 **안전하게** 처리되어 저장된 뒤,
그 저장값이 **나중에 다른 쿼리에 그대로 다시 결합**될 때 발생한다.
전형적인 발생 위치는 **세션/프로필 값**이다 — 로그인·가입 시점에 검증 없이 세션에 넣고,
이후 게시글 작성 같은 쓰기 쿼리에서 `Session("user")` 를 문자열 결합하는 패턴.

핵심은 **1차 요청은 정상 동작**하고, **2차 요청에서만 깨진다**는 점이다.
그래서 "로그인은 멀쩡히 되는데 게시가 안 된다" 같은 형태로 나타나고, 원인 파악이 늦어진다.

## 2. 케이스 — 세션 식별자에 따옴표가 들어간 상태로 쓰기 요청

```
1) 로그인 단계에서 세션 식별자에 ' 를 포함시킨다
   (로그인 SQLi 주석형 우회를 쓰면 비밀번호 없이도 가능 — authentication-bypass.md §2)
   POST /Login.asp   tfUName=admin'--  & tfUPass=x      → 302 (세션 획득)

2) 그 세션으로 게시글(리뷰/댓글) 작성
   POST /showthread.asp?id=<정수>  tfSubject=x & tfText=y
   → 500 (IIS 기본 오류 페이지, 애플리케이션 오류)
```

- **대조군이 필수**다: 따옴표 없는 정상 세션으로 **같은 요청**을 보내면 200 이어야 한다.
  두 응답의 **차이**가 곧 second-order 성립의 증거다(응답 코드를 단독으로 보면 "그냥 오류"와 구분 못 함).
- 행이 생성되지 **않은** 것을 확인한다(생성됐다면 다른 원인). 임팩트는 "게시 기능 파괴"(DoS 성격)다.
- **재확인된 사례**: `testasp-vulnweb-jev-trial`(Round 3)

## 3. 왜 이것을 별도 기법으로 기록하는가

- 같은 세션 식별자 하나가 **읽기 우회(auth bypass) · 쓰기 파괴(second-order) · XSS(무이스케이프 렌더)**
  세 갈래로 갈라진다 — 한 곳의 결함을 세 번 다른 각도에서 보고해야 누락이 없다.
- 진단 도구로는 잘 안 잡힌다(1차 요청은 정상). **세션/저장값이 다시 쓰이는 지점**을 소스에서 찾는 것이 빠르다:
  소스에서 `Session.Contents("...")` / `Session("...")` 를 검색해 **SQL 문자열 결합에 쓰이는 곳**을 본다.

## 4. 방어 관점

- 저장값이든 세션값이든 **모두 같은 파라미터 바인딩 경로**를 통과시킨다("이미 검증된 값"이라는 가정 금지).
- 세션에는 DB 기본키/임의 토큰만 저장하고, 사용자 표시 문자열은 조회 시점에 DB 에서 가져온다.
- 게시(쓰기) 경로에 **예외 로깅**을 붙여 500 을 조용히 삼키지 않는다.
