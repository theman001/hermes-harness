# 정보 노출 — 소스 유출 경유 자격증명 노출 / 저장 시 평문 비밀번호

> 기존 초안의 `frontpage-metadata-disclosure.md`(메타데이터 노출)와 `path-traversal.md`(소스 유출)를
> 보완하는 문서. **자격증명이 어디에 어떤 형태로 남는가**를 기법 단위로 분리해 기록한다.

## 1. 원리

"정보 노출"은 그 자체로 낮은 등급이지만, **다음 단계의 입력**이 된다. 노출 지점은 세 층으로 나뉜다:

1. **소스 코드** — `include`/템플릿 LFI 로 애플리케이션 소스가 읽히면, 소스 안에 박힌 **DB 접속문자열**이 함께 나온다.
2. **설정 파일** — `web.config` 류(같은 LFI 로 함께 읽힘).
3. **데이터 저장 형태** — 인증 테이블의 비밀번호가 **해시 없이 평문**으로 저장되어 있으면,
   SQLi 한 번으로 전 사용자의 자격증명이 읽힌다.

## 2. 케이스 A — LFI → 소스 → DB 접속문자열 평문 (재확인 + 정리)

```bash
# 1) 소스 열람 (traversal = 소스 유출, path-traversal.md 참조)
curl -s "http://<target>/<템플릿>?item=db.asp" | grep -i "Provider="
# → Provider=SQLNCLI11;Server=(local)\SQL;Database=<db>;Uid=<user>;Pwd=<평문>
```

**기록 원칙**
- 확보한 접속문자열은 **증거 파일에 원문 보관**, 보고서 본문에는 **마스킹**(`Uid=<user>; Pwd=***`).
- 이 자격증명의 가치는 "SQLi 를 우회한다"가 아니라 **SQLi 를 패치해도 남는 지속성**이다
  (소스에서 자격증명을 지우지 않으면 재발) → 별도 finding 으로 분리해 기록한다.
- `Server=(local)\...` 형태면 **외부에서 직접 접속 불가** → "DB 직접 접속" 같은 확장은
  **미검증(잠재)** 으로만 적고, 같은 호스트 발판이 필요하다는 조건을 명시한다.

## 3. 케이스 B — 저장 시 평문 비밀번호 (UNION 1요청) ★

```bash
# 열수만 맞추면 1요청으로 임의 컬럼 열람 (sql-injection.md 케이스 F 참조)
curl -s -G --data-urlencode \
  "q=zzq')>0) UNION ALL SELECT 1,'U='+<id컬럼>,'P='+<pw컬럼>,0,0,0,GETDATE(),'','','' FROM <users> WHERE <id컬럼>=(SELECT MIN(<id컬럼>) FROM <users>)--" \
  "http://<target>/<검색>" | grep -oE "[UP]=[^<']*"
```

**★ 데이터 최소화 원칙(반드시 지킬 것)**
- 증명에는 **1행이면 충분**하다. `MIN(...)`/`TOP 1` 로 **샘플 1행만** 추출하고,
  전체 행 수는 `COUNT(*)` 로만 확인한다(대량 반출 금지).
- 보고서/채팅에는 **마스킹**(`admin → adm***`, `password123 → pas********`)해서 싣고,
  원문은 증거 파일에만 남긴다.
- 추출한 값으로 **타 사용자 계정에 로그인하지 않는다**(피해자 신원 사용). 대신
  "읽은 값으로 로그인 가능한 구조"임은 **본인이 만든 계정**으로 같은 경로를 재현해 증명한다.
- 파급 서술: 평문 비밀번호는 **타 서비스 재사용 위험**까지 번지므로, 앱 취약점 등급보다
  넓은 영향을 갖는다는 점을 보고서에 명시한다.

## 4. 케이스 C — 부수 노출(정찰 가속) 목록

재확인된 사례: `testasp-vulnweb-jev-trial`(Round 1·3·4)
- FrontPage 메타데이터(`/_vti_cnf/*`) → 파일 목록·서브웹명·수정시각 (기존 문서 참조)
- 서버 스택 노출: `Server`/`X-Powered-By` 헤더, 오류 페이지의 프레임워크 흔적
- **주의**: `_vti_cnf/<file>` 의 404 를 "파일 부재"로 단정하면 안 된다(실존 파일에도 404 가 나오는 반례 실측).

## 5. 방어 관점

- 소스/설정 파일을 웹에서 읽을 수 없게 하고(경로 결합 검증 + 권한 최소화),
  **비밀번호는 반드시 단방향 해시(bcrypt/Argon2) + salt** 로 저장한다.
- 접속문자열은 코드가 아닌 **비밀 관리 저장소**로 옮기고 정기 회전한다.
- DB 계정은 애플리케이션별 최소 권한으로 분리(교차 DB 접근 제거).
- 디렉터리 메타데이터/불필요 확장(FrontPage Extensions 등)은 제거한다.
