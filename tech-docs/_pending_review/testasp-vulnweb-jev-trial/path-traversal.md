# Path Traversal (Arbitrary File Read) — 재확인 + 출력 방식 차이 케이스

> 기존 초안(`동일 대상의 기존 초안/path-traversal.md`)과 **같은 파일명** →
> 승격 시 그 문서에 아래 두 항목만 병합한다.

## 재확인된 사례: `testasp-vulnweb-jev-trial`

기존 문서의 판정 프로토콜(대조군 동봉, 인코딩 규칙, 절대→상대 경로 변환, 읽을 파일 우선순위)이
같은 대상에서 전부 재현됨. 추가로 확인된 운영 특성 두 가지:

1. **파라미터 부재/파일 부재도 500** — 같은 500 이 "차단"인지 "예외"인지 상태코드만으로 구분 불가
   → 항상 **성공이 보장된 대조군**(템플릿 파일 등)과 쌍으로 판정한다.
2. **`include` 기반 템플릿 엔진에서는 traversal = 소스 유출** — 요청한 파일이 코드로 실행되는 경로
   (`item=<앱 파일>.asp`)까지 성립해, 소스 전량 열람 → 이후 모든 공격의 안전 조건(파괴적 분기 등)을
   사전에 파악할 수 있었다. **소스 유출이 가능하면 공격 전에 먼저 소스를 읽는다.**

## 신규 케이스 — 같은 프리미티브의 **두 번째 인스턴스: 래퍼 유무** ★

한 사이트에 동일 결함이 두 곳 있었고, **출력 방식이 달라 증거 품질이 갈렸다**:

| 인스턴스 | 동작 | 전략 |
|---|---|---|
| A (템플릿 래퍼) | 사이트 레이아웃(HTML)이 앞뒤로 붙고, 결과가 그 안에 삽입됨 | 그대로도 읽히지만 노이즈가 섞임 |
| B (raw) | **파일 내용만** 반환(래퍼 없음) | **증거로 우선 사용** — 원문 그대로라 보고서 인용이 깔끔 |

**판별 방법**: 같은 페이로드를 두 지점에 보내고, 응답에 래퍼 흔적(`<!DOCTYPE`/템플릿 주석 등)이
있는지 비교한다. 래퍼가 없는 쪽이 있으면 그쪽을 대표 PoC 로 삼는다.

```
A: GET /Templatize.asp?item=../../../../windows/win.ini     → 200 + 레이아웃 + [fonts]
B: GET /shownews.asp?item=../../../../windows/win.ini       → 200 + [fonts] 만 (래퍼 없음)
   (B 는 어느 페이지에서도 링크되지 않는 미링크 파일 — 정찰로 발견)
```

**교훈**: **결함은 링크된 페이지에만 있는 게 아니다.** 미링크 파일(`shownews` 류)은
디렉터리/파일명 정찰의 산출물에서만 드러나므로, 정찰 목록을 버리지 말고 **같은 취약 패턴이
있을 법한 미링크 엔드포인트에 같은 파라미터를 재시도**한다.

## 신규 케이스 — 부정(negative) 결과도 자산으로 남기기

같은 대상에서 아래는 **읽히지 않았고**, 재탐색 방지를 위해 기록한다:

```
item=<웹루트 밖 스크립트 디렉터리>/logInput.txt   → 깊이 1~5 전부 500 (대조군 200)
item=global.asa                                  → 500 (파일 부재)
```

- "차단되지 않았는데 파일이 없다"와 "차단된다"는 다르다 → 깊이를 바꿔가며 확인하고,
  500 만으로 "차단됨"이라 쓰지 않는다.
- 로그/스크립트 디렉터리(`C:\scripts` 류)는 **설정에서 경로를 확인할 수 있으면 그 경로로만** 시도한다.

## 방어 관점(추가분)

- 파일 읽기 파라미터는 **허용 목록(정해진 템플릿 이름)** 으로만 처리하고, 경로 결합 후
  `realpath` 검증으로 루트 이탈을 차단한다.
- 웹루트 밖 스크립트/설정 디렉터리를 웹 서비스 계정 권한에서 제거(읽기 실패가 곧 방어).
- 템플릿/include 기능에 사용자 입력을 직접 넣지 않고, **ID → 고정 경로 매핑**을 둔다.
